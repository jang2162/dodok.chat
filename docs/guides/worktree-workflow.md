# 워크트리 작업 흐름

이 저장소의 코드 변경 작업은 **기본적으로 워크트리에서 한다.** 병렬 작업이든 단일 작업이든 마찬가지다.
예외는 **브레인스토밍도 스펙 명세도 구현계획도 없이 바로 구현에 들어갈 수 있는 작업**이고, 그 기준은 0절에 있다.

최상위 체크아웃(`.worktrees/` 가 아닌 원본 디렉터리)은 혼자 쓰는 작업 공간이 아니라 **공유 자원**이다.
IDE, 실행 중인 `pnpm dev`(Vite 개발 서버·서버 프로세스), 다른 에이전트 세션이 동시에 그 디렉터리를 보고 있다.

## 세 줄 요약

1. **일을 시작하기 전에 워크트리가 필요한 작업인지 먼저 정한다.** 기본값은 워크트리, 예외는 브레인스토밍·스펙·계획 없이 바로 구현할 수 있는 작업. → 0절
2. **메인 세션은 브랜치를 갈아타지 않는다.** `checkout` / `switch` 대신 워크트리를 만든다. 직접 처리하는 경우에도 마찬가지다. → 1절
3. **워크트리로 가는 작업에서 메인 세션은 디스패치·판정·병합만 한다.** 구현·리뷰·테스트 실행은 전부 워크트리 안의 워커(Orca 로 띄운 Claude 세션)가 한다. → 3·4절

## Orca 가 살아 있으면 Orca 워커가 우선이다

`orca status --json` 에 running runtime 이 보이면 **워크트리로 가는 작업의 실행 주체는 Orca 워커다.**
띄우는 명령은 `scripts/orca-worker.sh` 하나로 통일한다.

- **superpowers 는 브레인스토밍·스펙·구현계획까지만 쓴다.** 그 뒤의 구현·리뷰·검증은 워커에게 간다.
  `subagent-driven-development` 의 Agent 디스패치, `EnterWorktree`, 백그라운드 서브에이전트(Agent 도구)는
  **Orca 가 살아 있는 동안 구현 경로로 쓰지 않는다** — 서브에이전트는 컨텍스트가 조율자 안에 숨어 사람이 볼 수
  없고, `EnterWorktree` 가 만드는 `.claude/worktrees/` 는 이 저장소의 워크트리 규약(`.worktrees/dodok.chat/<슬러그>`)
  밖이라 `status`·`reap`·훅이 알지 못한다.
- **Orca 가 없거나 죽어 있거나, 살아 있어도 이 저장소의 워크트리를 다룰 수 없으면**(Orca 가 만드는 자리가 `.worktrees/dodok.chat/<슬러그>` 가 아닐 때 — 2절)
  그때만 superpowers 의 실행 경로(`subagent-driven-development`, 필요하면 `EnterWorktree`, 또는 손으로 만든
  `.worktrees/dodok.chat/<슬러그>` 안에서 도는 서브에이전트)로 내려간다. 내려갈 때는 그 이유를 사용자에게 말한다. 그 경우에도 5절(커밋)과 0절(판단)은 그대로 적용된다.
- 구현계획(`docs/superpowers/plans/*.md`)이 있으면 **브리프는 그 계획의 태스크를 가리키고**, 워커가 계획 문서를
  읽는다. 계획 본문을 브리프에 붙여 넣지 않는다.

## 0. 워크트리를 쓸지 판단하기

작업을 시작하기 전에 이것부터 정한다. **기본값은 워크트리다.** 아래 조건을 **전부** 만족할 때만 최상위 체크아웃에서 직접 고친다.

### 직접 처리해도 되는 것 — 브레인스토밍·스펙·구현계획 없이 바로 구현 가능한 작업

**기준은 변경의 크기가 아니라 "지금 바로 구현에 들어갈 수 있느냐"다.** 파일 개수는 기준이 아니다 — 여러 파일에 걸치더라도
무엇을 어떻게 고칠지가 이미 확정돼 있으면 직접 처리한다.

- **브레인스토밍이 필요 없다.** 요구사항을 되물어 좁히거나 선택지를 늘어놓을 필요가 없다.
- **스펙 명세나 구현계획을 먼저 쓸 필요가 없다.** 설계 선택지가 없고, 요청만으로 무엇을 어떻게 고칠지가 확정된다.
- **되돌리기 쉽다.** 실수해도 커밋 하나 되돌리면 끝난다.
- **브랜치를 갈아탈 필요가 없다.** 현재 브랜치에 그대로 커밋할 수 있다 — 1절(최상위에서 `checkout`/`switch` 금지)은 이 경우에도 그대로 유효하다.

예: 오타·문구 수정, 주석 정리, 문서(`.ruler/AGENTS.md`, `docs/*`) 갱신, 상수·설정값 조정, 린트·포맷터·훅 같은 지침·설정 갱신,
로그 메시지 추가, 이미 진단이 끝난 버그 수정, 정해진 패턴을 여러 파일에 똑같이 적용하는 기계적 변경.

이때는 메인 세션이 직접 고치고 커밋한다. 워커를 띄우지 않고, 리뷰어도 띄우지 않는다 — 워크트리 한 벌을 세팅하고
(`pnpm install`, `.env` 복사) 워커를 기동하는 비용이 변경 자체보다 커지는 구간이다. 커밋은 5절대로 경로를 명시해 stage 한다.

### 워크트리로 가는 것

하나라도 걸리면 워크트리를 만든다.

- **브레인스토밍·스펙 명세·구현계획이 먼저 필요하다.** 요구사항이 덜 정해진 신규 화면·기능, `shared` 스키마나 DB 스키마
  변경처럼 설계 판단이 따라오는 작업. 여러 레이어(`shared` 스키마·서버 모듈·플러그인·화면)에 걸치더라도 무엇을 어떻게
  만들지 이미 확정돼 있으면 이 조건에 걸리지 않는다.
- **새 브랜치가 필요하다.**
- **빌드·테스트를 반복해서 돌려야 한다.** 최상위에서 `pnpm dev`·watch 가 돌고 있으면 서로 방해한다.
- **여러 작업이 동시에 진행 중이라 파일이 겹칠 수 있다.**
- **판단이 애매하다.** 애매하면 워크트리다 — 워크트리를 만드는 비용은 몇 분이지만, 공유 체크아웃을 어질러 놓는 비용은
  사람의 IDE·실행 중인 서버까지 간다.

### 직접 작업 중에 범위가 커지면 즉시 옮긴다

"바로 구현하면 되는 줄 알았는데 아니었다"가 실제 이탈 경로다. **설계 판단이 필요해지거나, 스펙·구현계획을 먼저 써야 할
상황이 되거나, 빌드·테스트를 반복해 돌리게 되면 거기서 멈춘다.** 그대로 밀고 나가지 않고 워크트리로 옮겨 이어간다.

```bash
git stash                                                # 최상위를 원래대로 되돌린다
git worktree add -b feat/x .worktrees/dodok.chat/feat-x
(cd .worktrees/dodok.chat/feat-x && git stash pop)       # 워크트리에서 이어서 작업
```

## 전체 흐름

워크트리로 가기로 판단한(0절) 작업의 흐름이다.

```
[메인 세션 — 최상위 체크아웃]
  1. orca status --json                      # Orca 환경인지 먼저 확인
  2. git worktree list                       # 같은 작업의 워크트리가 이미 있는지 확인
  3. scripts/orca-worker.sh spawn <슬러그> implement --brief <브리프>
     → 워크트리 생성 · pnpm install · .env 복사 · BrowserOS neo 확인 · Task 생성 · 워커 기동 · 제출 확인
  4. scripts/orca-worker.sh wait             # worker_done 수신 (exit 3 은 타임아웃 — 다시 부른다)
  5. scripts/orca-worker.sh attach <슬러그> review --brief <리뷰브리프>   # 같은 워크트리에 새 에이전트로 띄운 리뷰어
     → 4번에서 구현자의 끝을 받은 뒤에 부른다(구현자의 Dispatch 가 진행 중이면 거부한다)
     → 구현자 터미널을 끄려면 그 앞에 scripts/orca-worker.sh stop <슬러그>(`--force` 없이 — 「워커가 도는 중이다」로 거부되면 구현자가 아직 도는 것이다)
       (워크트리 단위라 리뷰어를 띄운 뒤에 부르면 리뷰어도 끈다)
  6. 두 보고를 두고 무엇을 고치고 무엇을 이월할지 판정 · git diff --name-only 로 파일 목록 대조
  7. 병합 후 scripts/orca-worker.sh reap <슬러그>
```

3번에서 워크트리만 만들고 **메인 세션이 워크트리 안의 파일을 직접 고치는 것**, 또는 Orca 대신 서브에이전트(Agent 도구)를
쓰는 것이 가장 흔한 이탈이다. 아래 "판단 지점" 절 참고. 6번을 **메인 세션이 직접 diff 를 뜯어보는 것**으로 읽는 것도 같은
이탈이다 — 4절 참고.

## 1. 최상위 프로젝트에서는 브랜치를 체크아웃하지 않는다

**최상위 프로젝트 디렉터리에서는 브랜치를 `checkout` / `switch` 하지 않는다.**

- **Why:** 최상위의 `HEAD` 를 옮기면 그 디렉터리를 보고 있는 다른 작업·IDE·실행 중인 `pnpm dev`·Vite HMR 이 전부
  영향을 받는다. 동시 작업이 하나도 없어 보여도 사람이 켜 둔 IDE·서버는 남아 있다.
- **How to apply:**
  - 다른 브랜치에서 작업해야 하면 브랜치를 갈아타지 말고 **워크트리를 새로 만든다** (`git worktree add`).
  - 최상위에서 허용되는 것은 읽기 작업(`status`, `log`, `diff`, `show`, `fetch`)과 워크트리 관리(`worktree add/list/remove`),
    그리고 병합이다.
  - 체크아웃이 꼭 필요하면 **먼저 사용자에게 확인**을 받는다.
  - 워크트리 내부에서는 그 워크트리의 브랜치를 자유롭게 다뤄도 된다.

## 2. 워크트리 생성

### 먼저 — `scripts/orca-worker.sh spawn` 이 이 절을 대신 밟는다

Orca 환경이면 아래 한 줄이 이 절과 3절의 검증을 전부 수행한다.

```bash
scripts/orca-worker.sh spawn <슬러그> <역할> [--model opus|sonnet] [--brief <파일>] [--base <브랜치>]
```

스크립트가 밟는 단계 — **전부 아래에 이미 적혀 있던 것들이고, 사람이 반복해서 빠뜨리는 것들이다.**

1. `orca status --json` 으로 running runtime 확인 → 아니면 즉시 실패(조용한 이탈 차단)
2. `--base` 가 없으면 `git branch --show-current` 를 기준으로 쓴다 → `origin/main` 기본값 사고 차단
3. `orchestration run-current` 로 **Run 바인딩 확인** → 없으면 `run-create`.
   **워크트리를 만들기 전에** 한다 — 여기서 실패하면 잔해가 남지 않는다
4. `orca worktree create --base-branch <base> --setup run`
5. `git rev-list --count <새브랜치>..<base>` 가 0 인지 검증 → 아니면 `reset --hard`
6. `node_modules` 가 있는지 확인 → 없으면 `pnpm install`. Node 는 `mise.toml` 핀(24.21.0) — Orca 터미널은 대화형 zsh 라 `mise activate` 가 잡고,
   워커의 Bash 도구는 SessionStart 훅 `.claude/hooks/node-env.sh` 가 잡는다(mise 신뢰는 경로 단위라 spawn·sync-config 가 워크트리의 `mise.toml` 을 `mise trust` 한다). `node -v` 가 22 면 `export PATH="$(mise where node)/bin:$PATH"`(`.npmrc engine-strict` 라 22 에서는 `pnpm install` 이 실패한다).
   이어서 **최상위의 `.env` 를 워크트리로 복사한다**(`sync_local_config`) — gitignore 라 워크트리에 따라오지 않는다(아래 「생성 직후 세팅」).
   마지막으로 **BrowserOS neo 가 떠 있는지 확인하고 꺼져 있으면 켠다**(`ensure_browser`) — 워커는 `/mcp` 를 못 누르므로
   워커가 뜨기 전에 브라우저가 떠 있어야 한다(4절 「예외」)
7. `task-create --spec <브리프본문> --task-title <역할:슬러그>`
   → `worker-start --task --worktree id:<id> --agent claude --model <역할별> --timeout-ms`
   — **브리프는 `--spec` 으로 간다.** `worker-start` 에 `--prompt-file` 이라는 플래그는 없다.
   **터미널은 스크립트가 만들지 않는다** — 아래 「붙이기」 절 참고
8. `terminal wait --for tui-idle` 로 **화면이 그려질 때까지** 기다린다.
   여기의 `tui-idle` 은 붙이기 게이트가 아니라 렌더 대기다 — 붙이기는 이미 끝났다.
   이 대기가 없으면 다음 단계가 상태줄을 보기도 전에 시도를 소진한다
9. `terminal read --screen` 으로 `Ctx Used` 를 봐 제출을 확인(0.0% 면 엔터 재전송)

제목은 `terminal rename` 으로 `<역할>:<슬러그>` 를 붙이지만 **없어도 되는 단계다** —
에이전트가 곧 자기 상태로 덮고, 스크립트의 다른 동작은 전부 워크트리 경로로 한다.

**3번을 빼면 나머지가 전부 정상인데도 spawn 이 죽는다.** Run 은 코디네이터 터미널에 묶이므로
**세션이 바뀌면 이전 Run 은 재사용되지 않는다** — `run-list` 에 보이는 것과 바인딩된 것은 다르다.
바인딩 없이 `task-create` 를 부르면 `run_required` 로 거부된다. 스크립트는 그 오류 본문을 함께 낸다.

**중간에 하나라도 실패하면 거기서 멈춘다** — task 를 못 만들었는데 터미널만 띄우거나,
`worker-start` 가 실패했는데 성공 요약을 내지 않는다. 그런 워커는 supervised 로 잡히지 않아
`worker-release` 로 회수할 터미널 자원이 없다.

**⚠ spawn 이 재지 않는 것이 하나 있다 — 워크트리가 생기는 자리.** 스크립트는 워크트리 경로를
`<최상위>/.worktrees/dodok.chat/<슬러그>` 로 알고 그 자리에서 id 를 되찾는다. 그 자리는 Orca 의 worktree 경로 설정이
정한다 — **앱의 글로벌 설정이 기본이고 repo 별 `worktreeBasePath` 가 있으면 그것이 덮는다.** 이 머신은 글로벌 설정이
`.worktrees` 라 repo 별 값이 비어 있어도 `.worktrees/dodok.chat/<슬러그>` 에 만들어진다(실측: `orca worktree create` 의
반환 `path`). 둘 다 다른 값이면 Orca 는 다른 자리에 만들고 스크립트는 아무것도 찾지 못해 `spawn: 워크트리 생성 실패` 로
끝난다 — 워크트리는 실제로 만들어졌고 엉뚱한 자리에 잔해로 남는다. 이 메시지를 만나면 생성이 아니라 **설정을 의심한다.**
아래 「만드는 방법」의 경로 항목대로 재고 고친 뒤, `orca worktree list --json` 으로 잘못된 자리의 잔해를 찾아
`orca worktree rm` 으로 지우고 다시 spawn 한다.

### 붙이기 — 터미널을 직접 만들지 않는 이유

`worker-start` 는 **터미널을 스크립트가 만들어 넘기는 형태(`--terminal <핸들>`)와 Orca 가
직접 띄우는 형태(`--agent claude --model <모델>`) 둘 다** 받는다. `spawn` 은 뒤쪽을 쓴다.

- **`terminal create` 로 띄운 터미널은 한동안 붙지 않는다.** 그 창에서 `worker-start` 는
  `agent_unconfigured`(*Terminal … is not running a recognized agent*)로 거절한다.
  같은 인자를 1분쯤 뒤에 부르면 붙는다 — **갈리는 것은 재시도 횟수가 아니라 경과 시간이다.**
- **`terminal list` 의 `agentIdentity` 는 그 게이트가 아니다.** 거절당하는 순간에도 `"claude"` 로
  나온다. `terminal wait --for` 가 아는 조건은 `exit` 과 `tui-idle` 뿐이라 **스크립트 쪽에는
  그 등록을 기다릴 신호가 없다.** `tui-idle` 통과는 「붙일 수 있다」를 뜻하지 않는다.
- 그래서 기다리는 일을 게이트를 아는 쪽에 넘긴다. `--agent` 를 주면 Orca 가 에이전트를 띄우고
  붙이기까지 한 호출 안에서 하므로 **「띄웠지만 아직 붙일 수 없는」 구간 자체가 없다.**
  `--timeout-ms` 로 그 호출의 예산을 준다(`ORCA_WORKER_START_TIMEOUT_MS`, 기본 180000).
- **퓨즈는 둘이다** — 시간 예산(`ORCA_WORKER_ATTACH_BUDGET_SEC`, 기본 240초)과 시도 횟수 상한
  (`ORCA_WORKER_ATTACH_MAX_TRIES`, 기본 8회). 예산 하나만 두면 **그 값이 정수가 아니거나 시계가
  뒤로 가는 순간 루프가 끝나지 않는다** — `[ 5 -ge abc ]` 는 rc=2 로 죽고 `if` 가 그것을 거짓으로
  삼킨다. 값이 정수가 아니면 알리고 기본값으로 되돌린다. 시간 예산은 벽시계 상한이 **아니다** —
  검사가 호출 뒤에 오므로 최악은 `예산 + worker-start 한 번의 --timeout-ms + 간격` 이다.
- **`--model`·`--effort` 는 `--terminal` 과 함께 쓸 수 없다.** 이미 도는 에이전트의 모델은
  바꿀 수 없으므로, 붙이기만 하는 `attach` 는 `--model` 을 넘기지 않는다.

### 붙인 뒤에는 화면이 그려질 때까지 기다린다

`worker-start` 가 성공을 반환해도 그것은 **전송 성공**까지만 보증한다. 미제출을 잡아 엔터를
다시 보내는 장치는 상태줄의 `Ctx Used` 를 읽는데, **갓 뜬 TUI 는 상태줄을 아직 그리지 않았다.**
그래서 붙인 뒤 `terminal wait --for tui-idle` 로 한 번 기다리고, 상태줄을 못 읽는 동안에도
시도 사이에 쉰다(`ORCA_WORKER_SUBMIT_TRIES`·`ORCA_WORKER_SUBMIT_SLEEP`).

**대기 없이 시도를 태우면 세 번이 0.5초에 끝나 「미제출 → 엔터 재전송」 갈래에 영원히
도달하지 못한다.** 그때 남는 것은 성공할 때마다 찍히는 경고뿐이고, 그 경고가 쌓이면 진짜
미제출 경고까지 무시하게 된다. 여기의 `tui-idle` 은 붙이기 게이트가 아니라 렌더 대기다.

### 상태줄은 화면 전체가 아니라 한 줄이다 — 앵커와 NBSP

미제출 판별(`0.0%` → 엔터 재전송)은 `orca terminal read --screen --json` 의 응답을 읽는다.
그 응답에는 **두 개의 함정**이 있고, 둘 다 조용하다.

#### 1. 낱말 사이가 보통 공백이 아니다

상태줄에서 `Ctx` 와 `Used` 사이, `:` 뒤, 게이지와 퍼센트 사이는 전부
**U+00A0 NO-BREAK SPACE**(UTF-8 로 `0xc2 0xa0`)다. 보통 공백(`0x20`)이 아니다.
원문을 `od` 로 재면 이렇게 나온다.

```
C t x c2a0 U s e d : c2a0 <게이지> c2a0 1 2 . 0 %
```

**`grep 'Ctx Used'` 는 여기에 절대 맞지 않는다.** 맞지 않으면 상태줄을 영원히
「아직 안 그려졌다」로 읽어 시도를 다 태우고, **미제출 방어에 한 번도 도달하지 못한다** —
그 갈래가 이 장치의 존재 이유다. 그리고 그 실패는 조용하다: 성공한 `spawn` 마다
「확인하지 못했다」 경고가 한 줄 찍힐 뿐이라, 대기를 아무리 늘려도 낫지 않고 경고가 쌓여
진짜 미제출까지 묻힌다.

- 패턴은 **보통 공백과 NBSP 를 둘 다** 받는다(`Ctx( |<NBSP>)Used`). 런타임이 보통 공백으로
  바뀌어도 계속 맞아야 한다.
- **대괄호가 아니라 교체(`|`)를 쓴다.** `[ <NBSP>]` 는 C 로케일에서 한 바이트만 세어
  두 바이트짜리 NBSP 를 놓친다. **그 회귀는 UTF-8 로케일에서 초록으로 통과하고
  컨테이너·cron·launchd 에서만 깨지므로, 테스트가 `LC_ALL=C` 를 명시로 걸어 잰다.**
  (손으로 잴 때 주의 — 대화형 셸의 `grep` 이 `ugrep` 이면 대괄호도 통과해 규칙이 거짓처럼 보인다.
  비대화형 셸의 `/usr/bin/grep` 으로 재라.)

#### 2. 화면에는 상태줄만 있는 것이 아니다

`--screen` 이 내는 것은 **렌더된 화면**이고, 거기에는 워커가 읽은 브리프·문서·자기 출력이
그대로 떠 있다. 그 산문에 `Ctx Used` 라는 글자가 있으면 두 갈래가 함께 깨진다.

| 화면 | 응답 전체를 훑으면 | 옳은 판정 |
|---|---|---|
| 상태줄이 아직 없고 스크롤백에만 `Ctx Used` | **「제출됨」 · 경고 0줄** | 미제출 |
| 상태줄은 11.0% 인데 스크롤백 한 줄에 `Ctx Used … 0.0%` | **거짓 미제출 → 도는 워커에 엔터 재전송** | 제출됨 |

**그리고 이 규칙 자체가 산문이다.** 이 절을 인용하는 브리프로 워커를 띄우면 그 브리프
본문이 화면에 떠서 탐지를 만족시키고, **그 워커의 미제출 탐지가 꺼진다.**

그래서 **`.result.terminal.tail` 에서 상태줄 한 줄만 골라** 거기에만 `0.0%` 를 잰다.
조건은 둘이고, 맞는 것이 여럿이면 **마지막**을 고른다.

1. 앵커(`Ctx<공백류>Used`)에 맞는다.
2. **퍼센트를 같은 줄에 갖는다.** 산문은 앵커와 퍼센트를 한 줄에 같이 갖지 않는다.

화면 맨 아래가 상태줄이므로 `last` 가 그것이다 — 스크롤백은 언제나 그 위에 있다.

- 상태줄이 함께 갖는 `⎇ <브랜치>` 는 **필수 앵커로 쓰지 않는다.** 그것까지 요구하면
  서식이 조금만 달라져도 매번 「상태줄을 못 읽었다」로 떨어져, 이 장치가 없애려는
  경고 홍수가 그대로 돌아온다.
- **응답 모양이 달라지면 빈 줄이 나오고, 그것은 「못 읽었다」다** — 「제출됨」으로 넘어가지
  않는다(fail closed).
- **테스트 픽스처는 실물의 세 성질을 다 갖춰야 한다** — 진짜 NBSP 바이트, `tail` 배열과
  여러 줄 pretty-print, 그리고 **스크롤백이 함께 든 화면**. 상태줄만 든 픽스처는 위 두 칸을
  아예 재지 못한다.

### `attach` 는 `.env` 를 덮지 않는다

`spawn` 은 새 워크트리라 최상위 값으로 덮는 것이 맞다. `attach` 는 **이미 사람이나 워커가 손댄 워크트리**에
적용되는 복구 경로이므로 덮지 않는다 — **없을 때만 채우고, 다르면 알리고 그대로 둔다.** `.env` 는 gitignore 라
되돌릴 이력이 없고, 워커가 바꿔 둔 포트·DB 경로를 덮으면 **워크트리 앱이 최상위 앱과 같은 포트·DB 를 두고
충돌한다** — 로그에는 접속 오류만 찍혀 설정이 바뀐 것이 보이지 않는다.

최상위 값으로 맞추고 싶으면 `scripts/orca-worker.sh sync-config <경로>` 를 명시로 부른다.

### 붙이기가 실패했을 때 — 워크트리를 버리지 않는다

`spawn` 이 붙이기에 실패해도 `pnpm install`·`.env` 복사가 끝난 워크트리와 살아 있는 터미널은
그대로 둔다. 실패한 Task 는 `failed` 로 잠겨 재시작할 수 없으므로 **Task 만 새로 세워 다시 붙인다.**

```bash
scripts/orca-worker.sh attach <슬러그> <역할> [--model ...] [--brief <파일>] [--terminal <핸들>] [--force]
```

`attach` 는 워크트리를 새로 만들지 않는다. 그 워크트리에 살아 있는 에이전트
터미널이 있으면 그중 목록의 마지막을 쓰고, 하나도 없으면 `--agent` 로 새로 띄운다.
**`review` 는 예외다 — `--terminal` 이 없으면 살아 있는 터미널이 있어도 늘 새 에이전트를 띄운다.**
끝난 구현자의 터미널에 붙이면 리뷰가 구현자 자신의 문맥에서 돌아 독립 리뷰가 아니다. `--terminal` 을 준
리뷰는 사람이 고른 것이므로 그대로 받는다.

- **진행 중인 Dispatch 가 붙어 있는 터미널에는 붙이지 않는다.** 그 워커는 이미 브리프를
  받고 일하는 중일 수 있고, 다시 붙이면 **같은 지시가 두 번 주입된다.** 터미널을 먼저 읽어
  확인하고, 확인하고도 붙이려면 `--force`.
  **`review` 는 그 터미널에 붙지 않아도 구현자의 Dispatch 가 아직 진행 중이면 거부한다** — 반쯤 된
  트리를 리뷰하고 두 에이전트가 한 워크트리를 함께 고치게 된다(리뷰어의 변이 테스트도 파일을 잠시
  고친다). `wait` 로 끝을 받은 뒤 붙이고, 확인하고도 띄우려면 `--force`.
  **`worker-list` 를 끝까지 읽지 못하면 Task 를 만들기 전에 거부한다** — 다시 부르거나 `--force`.
  `worker-list` 를 끝까지 읽지 못했을 때 `--force` 는 진행 중 검사와 `--retry-of` 없이 붙인다 — 실패한
  직전 시도와의 이력이 끊긴다.
- **리뷰어를 띄울 때 남은 에이전트 터미널은 그대로 둔다.** `attach` 가 그 핸들을 보여 준다. 정리하려면
  리뷰어를 띄우기 **전에** `scripts/orca-worker.sh stop <슬러그>` — **`--force` 를 붙이지 않는다.**
  끝난 구현자는 회수된 뒤 꺼지고, 「워커가 도는 중이다」로 거부되면 구현자가 아직 도는 것이다
  (다른 exit 1 은 「터미널을 끄는 것은 `stop` 이 한다」 절). `--force` 로 끄면 그 터미널이 사라져
  `attach` 의 진행 중 Dispatch 거부가 볼 것이 없어진다. 띄운 뒤라면 그 핸들만 끈다
  (`orca terminal close --terminal <핸들>` — `attach` 가 핸들마다 찍어 준다). **`stop` 은 워크트리
  단위라 리뷰어를 띄운 뒤에 부르면 방금 띄운 리뷰어까지 문맥째 끈다** — 리뷰어가 도는 중이면 `stop` 이
  거부하지만 `--force` 를 붙이면 뚫린다. 리뷰까지 끝난 뒤(`reap` 앞)에는 워크트리 단위 `stop` 을 써도 된다.
- **리뷰 뒤에는 워크트리에 구현자·리뷰어 터미널이 함께 남는다.** `--terminal` 없는 `attach` 는 그중
  목록의 마지막을 쓰므로, 수정을 특정 세션에 맡기려면 `--terminal <핸들>` 을 준다.
- **`spawn` 이 「브리프는 전달됐다」고 말했으면 `attach` 를 부르지 마라.** 같은 이유다.
- **`--terminal <핸들>` 은 그 핸들이 이 워크트리 것인지 확인한 뒤에만 받는다.** 확인 없이
  넘기면 다른 워크트리(다른 프로젝트일 수도 있다)에서 도는 워커에 브리프가 주입된다.
  이것은 중복 주입이 아니라 오폭이므로 **`--force` 로도 뚫지 않는다.**
- **그 터미널의 직전 Dispatch 가 `failed` 일 때만 `--retry-of` 로 잇는다.** 없으면 이력이 끊긴다.
  **성공한 Dispatch 는 잇지 마라** — 새 Task 는 그것의 재시도가 아니고, `worker-start` 가
  `task_not_startable` 로 거절해 붙이기가 통째로 실패한다. 정상 종료한 워커의 터미널에
  다음 역할(`verify`·`chore` 등)을 붙이는 것이 `attach` 의 흔한 쓰임이라 **이 구멍은 정확히 그 자리에서 열린다.**
  구현 → 리뷰는 `attach` 가 새 에이전트로 띄운다 — 리뷰어는 구현자와 다른 세션이어야 한다.
  그리고 **최신(`first`)을 고른 뒤에 상태를 본다** — `worker-list` 는 최신순이라 직전 시도는 그
  터미널의 첫 행이다. 실패한 것만 먼저 걸러 첫 행을 잡으면 그 뒤(더 최근)에 성공이 있어도
  **옛 실패를 끌어와** 잇는다. 이을 것은 「교체하는 그 시도」뿐이다.

### 재시도 전에 「이미 먹혔는가」를 묻는다

붙이기가 실패했다는 응답이 **아무 일도 없었다는 뜻은 아니다.** 실패 응답에 브리프 주입이
끝났다고 적혀 있을 수 있다 — 그 워커는 붙지 않은 채 정상적으로 일을 마친다.
그래서 재시도는 응답을 판정한 뒤에만 한다.

- 실패 응답의 `error.data.effects` 에 `dispatch_input`(`state: accepted`)이 있으면
  **브리프는 이미 워커에게 들어갔다.** 재시도 금지.
- `error.data.orchestrationRequestId` 를 `orchestration request-show --request <id>` 로 묻는다.
  `completed` 면 그 mutation 은 이미 먹혔다(재시도 금지). `pending` 이면 **같은 requestId 를
  `--retry-request` 로 되돌려 주는 것만** 안전하다 — 그래야 Orca 가 두 번째 작업을 시작하지
  않고 이어받는다. `absent` 는 **「아무 일도 없었다」의 증거가 아니다**(런타임이 그렇게 말한다).
- `error.data.effectsApplied` 가 `false` 일 때만 새로 부른다. **이 필드는 불리언이므로 jq 의
  `//` 로 꺼내면 안 된다** — `false // x` 가 `x` 로 넘어가 「효과 없음」이 「판정 불가」로 뒤집힌다.
- **`residualResources` 가 비어 있지 않으면 어떤 재시도도 하지 않는다.** 스킬 정본이
  실패 시 `stage`·`effects`·`residualResources` 를 보라며 *instead of guessing or
  automatically retrying* 라고 못박는다. 그 금지에는 조건이 없으므로 **위의 어느 갈래보다
  먼저 온다.** 무엇이 남았는지와 정본이 함께 주는 복구 명령을 그대로 조율자에게 낸다.
- **`stage`/`failedStage` 를 읽어 「어디까지 갔다가 실패했는가」를 함께 출력한다.**
  「판정 불가」 한 마디로 끝내면 조율자가 터미널을 손으로 뒤지러 간다.
- 판정할 수 없으면 **조용히 재시도하지 않고** 그 사실과 확인할 명령을 출력한다.

> **`worker-start` 실패 봉투에는 `effects` 도 `effectsApplied` 도 없을 수 있다** —
> `.error.data` 에 `orchestrationRequestId` 와 `originalCommand` 둘뿐인 형태가 실물이다.
> `effectsApplied` 는 다른 오류 부류에서 온다. 그래서 두 갈래를 지우지 않고 남기되,
> **그런 봉투는 전부 「판정 불가」로 떨어져 재시도하지 않는다.** 못 알아보면 판정 불가이고,
> 판정 불가는 재시도하지 않는다(fail closed).
>
> `task_not_found`·`terminal_handle_stale`·`selector_not_found`·`agent_unconfigured` 는 전부
> **「띄우기를 시작하기 전」의 검증 단계** 실패라 남은 자원이 없고 `stage`·`residualResources` 도
> 오지 않는다. 그 두 필드를 읽는 코드는 `worker-start --help` 계약에 근거한 구현이다 — 관측처럼 읽지 마라.
>
> **그래서 자리를 짚지 않고 봉투 전체를 이름으로 훑는다.** 자리를 하나 골라 거기만 보면 그 자리가
> 틀렸을 때 0건으로 읽히고, 봉투가 `effectsApplied:false` 를 함께 달고 있으면 그것이 `clean` 으로
> 떨어져 **재시도한다.** 남는 구멍은 이름 하나다 — 런타임이 다른 이름으로 부르면 못 찾는다.
> 그 칸을 테스트가 의도적으로 단언해 둔다.

### 붙지 못한 워커는 `wait` 로 잡히지 않는다

`scripts/orca-worker.sh wait` 는 supervised 워커의 `worker_done` 만 받는다. 붙이기에 실패한
워커는 **정상적으로 일을 마쳐도 완료 신호가 오지 않는다** — 조율자는 타임아웃까지 기다리고
결과는 터미널 안에만 남는다. `spawn`·`attach` 는 최종 실패 시 그 사실과 읽을 명령
(`orca terminal read --terminal <핸들> --screen --json`)을 함께 출력한다.

**아래 수동 절차는 지우지 않는다.** Orca 가 없는 환경에서 쓰고, 스크립트가 어긋났을 때
어디가 어긋났는지 짚는 근거가 여기에 있다.

### 만드는 방법 — **Orca 가 살아 있으면 Orca 로 만든다**

`orca status --json` 에 running runtime 이 보이면 **`orca worktree create` 를 먼저 쓴다.**

```bash
# 기준은 「지금 세션이 서 있는 브랜치」다. main 이라고 박아 두지 마라.
BASE=$(git branch --show-current)
orca worktree create --name <슬러그> --repo path:/Users/jang2162/IdeaProjects/dodok.chat \
    --base-branch "$BASE" --setup run --json
```

`git worktree add` 보다 나은 점 셋:

1. **Orca 가 곧바로 등록한다** — 반환 JSON 에 `id` 가 들어 있어 `orca worktree list --json` 으로 다시 찾을 필요가 없다.
   그 id 가 3절의 `worker-start --worktree id:<fullId>` 에 그대로 들어간다.
2. **`--setup run` 이 저장소 루트 `orca.yaml` 의 셋업을 돌린다** — mise·의존성 설치·`ruler apply`·`.env` 복사·codegraph 인덱스(아래).
3. `--agent` · `--prompt` 로 워크트리 생성과 워커 기동을 한 번에 할 수 있다(3절 참고).

**다만 세 가지를 반드시 확인한다.**

- **`--base-branch` 를 빼지 마라. 기본값은 `origin/main` 이고, 로컬 브랜치보다 뒤에 있을 수 있다.**
  이 저장소는 로컬에서 커밋하고 push 는 나중에 하는 흐름이라 `origin/main` 이 낡아 있는 것이 보통이다.
  옵션을 빼면 워크트리가 그만큼 낡은 코드로 시작하고, **워커는 방금 쓴 스펙 문서조차 찾지 못한다.**

  **넘길 값은 `main` 이 아니라 「지금 세션이 서 있는 브랜치」다.** 메인 세션이 `main` 에 있으면 `main` 이지만,
  다른 브랜치에 서 있는데 `main` 을 박아 넘기면 **그 세션이 방금 만든 커밋이 통째로 빠진다.**
  `git branch --show-current` 로 받아서 넘겨라.

  **`orca orchestration worker-start` 에도 같은 옵션이 있다**(`--base-branch <ref>`). 워크트리를 만드는 경로가
  `worktree create` 든 `worker-start --worktree new-top-level` 이든 **양쪽 다 넘겨야 한다.**
  넘겼더라도 워커를 띄우기 전에 **reflog 로 한 번 확인하는 것이 가장 싸다**:

  ```bash
  git reflog show <브랜치> | tail -1          # "Created from refs/heads/<기준>" 이어야 한다
  git rev-list --count <브랜치>..<기준브랜치>  # 0 이어야 한다
  ```

  **0 이 아니면 워커를 띄우기 전에 되감는다** — `git -C <워크트리> reset --hard <기준브랜치>`.
  `.env`·`data/`·`node_modules` 는 gitignore 라 `reset --hard` 로 날아가지 않는다.
  **이미 워커가 돌고 있었다면 커밋이 있어도 버리고 다시 띄우는 쪽이 싸다** — 낡은 기준에서 만든 커밋은
  리베이스가 충돌 범벅이 된다.

  **가르치는 자리가 둘이면 둘 다 맞아야 한다** — `.ruler/AGENTS.md` 요약에도 이 옵션이 들어 있다. 한쪽만 고치지 마라.

- **`--setup run` 이 무엇을 했는지 믿지 말고 재라.** 셋업은 저장소 루트의 `orca.yaml`(`scripts.setup`,
  `setupAgentStartupPolicy: wait-for-setup`)이 갖는다. **Orca 는 그 파일을 새 워크트리의 체크아웃에서 읽는다** — 커밋하지 않은
  `orca.yaml` 이나 기준 브랜치에 아직 없는 변경은 돌지 않고, 그래도 워크트리 생성은 성공한다(실측: 커밋 전 셋업 0회, 커밋 뒤
  `.env`·`node_modules`·`CLAUDE.md` 생성). 출처 정책은 **Orca 앱의 repo 설정**(`commandSourcePolicy` — 이 머신은 `shared-only`)이
  정하고 CLI 로는 못 바꾼다. 셋업이 안 돈 워크트리는 `spawn` 의 `verify_setup` 이 사후에 같은 단계를 채운다(멱등).
  손으로 만든 워크트리는 아래 「생성 직후 세팅」을 직접 밟는다.

  ```bash
  orca repo show --repo path:/Users/jang2162/IdeaProjects/dodok.chat --json \
    | jq '.result.repo.hookSettings | {commandSourcePolicy, setupRunPolicy}'
  ```
- **경로는 Orca 가 정한다 — 글로벌 설정 또는 repo 별 `worktreeBasePath`.** 워크트리 위치는 앱의 글로벌 worktree 경로
  설정이 기본이고, repo 설정의 `worktreeBasePath` 가 있으면 그것이 덮는다. **repo 를 Orca 에 등록해도 repo 별 값은 자동으로
  채워지지 않으며, 글로벌 값은 CLI 로 보이지 않는다**(`repo show` 에는 repo 별 값만 나온다). 어느 쪽도 `.worktrees` 가
  아니면 워크트리가 저장소 루트 밖으로 나갈 수 있고, 그렇게 생긴 워크트리는 **다른 에이전트가 찾지 못하고 `.gitignore` 도
  덮지 못한다**(아래 「Orca 가 없을 때」의 위치 규약).

  **설정을 읽지 말고 실물로 잰다** — 일회용 워크트리를 만들어 반환 `path` 를 보고 바로 지운다.

  ```bash
  orca worktree create --name probe-path --repo path:/Users/jang2162/IdeaProjects/dodok.chat \
      --base-branch main --setup skip --no-parent --json | jq -r '.result.worktree.path // .result.path'
  # /Users/jang2162/IdeaProjects/dodok.chat/.worktrees/dodok.chat/probe-path   ← 이 자리여야 한다
  orca worktree rm --worktree "id:<repoId>::<위 path>" --json && git worktree prune
  ```

  이 머신의 글로벌 설정은 `.worktrees` 이고 위 실측이 그 자리를 냈다. 다른 자리가 나오면 **Orca 앱 설정**(글로벌 또는
  그 repo 의 worktree 경로)에서 `.worktrees` 로 맞추고 다시 잰다. ⚠ **CLI 로는 이 값을 쓸 수 없다** — `repo add` 는
  경로만 받고, `repo set-base-ref` 는 기준 ref 를, `worktree set` 은 이름·이슈·부모 같은 메타데이터만 바꾼다.
  `worktree create` 에도 생성 위치를 받는 옵션이 없다(`--name` 은 이름이지 경로가 아니다). **고칠 수 있는 자리는 앱 설정뿐이므로,
  자리가 틀리면 거기서 멈추고 사람에게 설정을 바꿔 달라고 알린다** — CLI 로 우회하려다 엉뚱한 자리에 만들지 마라.

  `rm` 뒤에는 `.worktrees/dodok.chat/.orca-worktree-trash/` 가 남을 수 있다 — Orca 의 휴지통이지 잔해가 아니다.

  설정이 맞더라도 **만든 뒤 반환 JSON 의 `path` 를 보고** 그 자리가
  `<최상위>/.worktrees/dodok.chat/<슬러그>` 인지 확인한다 — `scripts/orca-worker.sh` 가 아는 자리가 여기다.
  아니면 **워커를 띄우기 전에** `orca worktree rm` 으로 지우고 설정을 고친 뒤 다시 만든다 — 잘못된 자리에
  워커를 붙이고 나면 그 워커가 만든 커밋까지 함께 옮겨야 한다.

### Orca 가 없을 때 (또는 위가 실패할 때)

```bash
git worktree add -b feat/<작업명> .worktrees/dodok.chat/<슬러그>
```

- **위치**: `.worktrees/dodok.chat/<슬러그>/` (저장소 루트 하위, gitignore 됨). Orca 가 만드는 자리와 같은 규약을 쓴다 —
  그래야 `status`·`reap`·훅이 손으로 만든 것도 다룬다. 저장소 바깥이나 임의 경로에 만들지 않는다.
- ⚠ **손으로(`git worktree add`) 만든 워크트리는 Orca 가 목록에 올리지 않는다**(이 저장소에서 실측 — 글로벌 설정이
  `.worktrees` 이고 자리도 규약대로였는데 `orca worktree list --json` 에 나오지 않았다). 그러면 `attach` 도
  「Orca 가 워크트리로 모른다」로 실패한다. **Orca 워커를 붙일 워크트리는 Orca 로 만든다(= `spawn`).** 손으로 만든
  워크트리에서 일해야 하면 그 안의 실행 주체는 문서 첫머리의 폴백(서브에이전트)이고, 그 이유를 사용자에게 말한다.
- 기준 브랜치를 명시해야 하면 마지막 인자로 준다(`... .worktrees/dodok.chat/x base2`). 기본은 현재 `HEAD` 다.
- superpowers 의 `EnterWorktree` 가 만드는 `.claude/worktrees/` 도 gitignore 돼 있지만 **Orca 가 살아 있을 때는 쓰지 않는다**
  (문서 첫머리 「Orca 워커가 우선이다」).

### 공통

- **브랜치**: 워크트리를 만들 때 **새 브랜치를 함께 만든다.** 이미 다른 워크트리가 체크아웃한 브랜치는 git 이 거부한다.
- **하나의 작업 = 하나의 워크트리.** 여러 작업을 한 워크트리에서 브랜치 갈아타며 처리하지 않는다.
- **작업 전 확인**: `git worktree list` 로 같은 작업의 워크트리가 이미 있는지 본다. 있으면 새로 만들지 말고 그것을 쓴다.

### 생성 직후 세팅

새 워크트리는 빈 체크아웃이다. 빌드·실행 전에 워크트리 안에서 직접 돌린다.

```bash
cd .worktrees/dodok.chat/<슬러그>
node -v                                   # 24.x 여야 한다 (mise.toml 핀; 아니면 export PATH="$(mise where node)/bin:$PATH")
pnpm install                              # node_modules 는 워크트리마다 따로 필요하다
scripts/orca-worker.sh sync-config .      # ruler apply(CLAUDE.md 등 생성물) + codegraph 인덱스 + 최상위 .env 복사 (아래 Why 참고)
pnpm typecheck && pnpm test               # 기준선 확인 — Turbo 캐시는 꺼져 있다 (아래 참고)
```

- **gitignore 대상인 로컬 설정은 따라오지 않는다.** `.env` 가 없으면 워크트리의 서버가 **환경 변수 없이 떠서**
  설정 검증에 실패하거나 다른 Gateway·DB 경로를 향한다 — 로그에는 접속 오류만 찍혀 설정이 빠진 것이 보이지 않는다.
  앱을 띄울 예정이면 최상위에서 복사부터 해라.
  **`scripts/orca-worker.sh spawn` 으로 만든 워크트리는 이 복사를 스크립트가 한다**
  (`sync_local_config` — `node_modules` 확인 바로 뒤). 손으로 만든 워크트리에는 같은 일을 하는 서브커맨드가
  있다 — **워크트리 안에서 불러도 최상위를 원본으로 잡는다.**
  ```bash
  scripts/orca-worker.sh sync-config .worktrees/dodok.chat/<슬러그>   # 경로를 빼면 현재 디렉터리
  ```
  스크립트를 쓸 수 없는 자리에서는 `cp .env .worktrees/dodok.chat/<슬러그>/.env` 로 같은 일을 한다.
  **최상위에 `.env` 가 아직 없으면**(Phase 0 전) 스크립트는 「환경 변수 없이」 경고만 내고 계속 간다 — 순수 함수와
  테스트만 다루는 작업에는 문제가 없고, 서버를 띄우는 작업이면 `.env` 를 먼저 만든다.
- **`data/` 는 복사하지 않는다.** SQLite 파일·업로드·디바이스 아이덴티티는 워크트리마다 따로 생긴다.
  `DATABASE_URL` 이 상대 경로(`file:./data/app.db`)라 워크트리 앱은 **자기 `data/` 에 새 DB 를 만들고 마이그레이션을
  돌린다** — 최상위 DB 를 건드리지 않는 것이 의도다. 최상위 데이터가 필요한 검증이면 브리프에 그렇게 적고 파일을 복사한다.
  ⚠ **디바이스 아이덴티티도 새로 생긴다.** 원격 Gateway 접속이 필요한 검증은 페어링을 다시 해야 하므로, 그 워크트리에
  최상위의 `data/gateways/<연결 id>/`(디바이스 아이덴티티·디바이스 토큰)를 복사하거나 페어링 절차를 브리프에 넣는다. 그리고 **원격 Gateway 의 플러그인은
  브리지 주소 하나에만 붙는다** — 브리지 경로가 필요한 검증은 **한 번에 한 인스턴스만** 돌린다. Phase 0 스파이크가
  이 절차를 확정하면 이 항목을 갱신한다.
- **워크트리 앱은 최상위 앱과 포트가 겹친다.** 서버 포트·Vite 포트·`APP_ORIGIN` 을 **함께** 최상위와 다르게 준다 —
  변수 이름은 `.env.example` 이 정본이다. 하나만 바꾸면 화면은 워크트리 것인데 API 는 최상위 것을 보는 인스턴스가 된다.
  **이렇게 띄우면 병합 전에 실화면을 볼 수 있다** — 최상위는 `main` 이라 워크트리의 변경이 없다.
  쿠키 세션이 들어오면 두 인스턴스가 같은 호스트의 쿠키 한 칸을 두고 서로를 덮으므로, 그때 세션 쿠키 이름을 가르는
  규칙을 [브라우저 검증](browser-verification.md) 「여러 세션이 동시에 볼 때」에 적는다.
  쿠키까지 가르는 명령은 [브라우저 검증](browser-verification.md) 「워크트리에서 앱을 띄울 때는 최상위와 포트를 갈라라」 항목이 갖는다.
  **실물 dev Gateway 에 붙는 실연 서버는 예외다** — 플러그인 계정 `bridgeUrl` 의 포트(`docs/guides/live-smoke.md` 「전제」 표)로 띄운다.
  병행 워커 포트 배정(`dev:fake` 3100 대)에서 빼고, 브리지가 한 번에 한 서버에만 붙으므로 그 실연은 한 번에 하나만 돌린다.
- **Turbo 캐시는 검증 결과를 재생할 수 있다.** 같은 입력이면 Turbo 는 태스크를 다시 돌리지 않고 **지난 출력을 재생하며
  「통과」를 찍는다** — 테스트를 고쳤는데도 옛 결과가 나오는 것이 아니라, 아무것도 안 바뀌었다고 판단하면 실행 자체를
  건너뛰는 것이다. 그래서 `turbo.json` 의 `test`·`typecheck` 는 `cache: false` 다. **검증 태스크를 새로 추가하면
  같은 설정을 준다.** 캐시가 켜진 태스크를 굳이 재실행하려면 `pnpm turbo run <task> --force`.

이 세팅은 워커를 띄우기 전에 메인 세션이 해 두는 편이 낫다(`spawn` 은 이미 그렇게 한다). **"실행은 전부 워커가 한다"(4절)의
유일한 예외가 이것이다** — 워커가 아직 없으니 편집이 충돌할 상대가 없다. 대신 **서브셸로 돌려 메인 세션의 셸이 워크트리에
눌러앉지 않게 한다.**

```bash
(cd .worktrees/dodok.chat/<슬러그> && pnpm install && scripts/orca-worker.sh sync-config . && pnpm typecheck)
```

## 3. 워크트리에 Claude 세션 띄우기 (Orca)

워크트리를 만들었으면 **그 워크트리에서 돌 Claude 세션을 Orca 로 띄운다.** 메인 세션이 워크트리 안으로 들어가 직접 파일을
고치지 않는다. 백그라운드 서브에이전트(Agent 도구)보다 Orca 터미널 워커가 우선이다.

- **Why:** Orca 터미널 워커는 앱에 **독립 터미널**로 떠서 사람이 진행을 직접 보고 개입할 수 있고, Orca 태스크/디스패치
  이력(provenance)이 남는다. 서브에이전트는 컨텍스트가 코디네이터 안에 숨어 보이지 않는다. 메인 세션이 직접 작업하면
  워크트리를 나눈 의미(격리·관찰 가능성)가 사라진다.
- **환경 확인:** `orca status --json` 이 running runtime 을 보이면 Orca 환경이다. (CLI 실행자: `ORCA_CLI_COMMAND` 가 있으면
  그 값, 없으면 macOS·일반은 `orca`, **Linux 는 `orca-ide`** — 리눅스에서 bare `orca` 는 GNOME 스크린리더로 붙는다.)
  오케스트레이션 experimental 기능이 켜져 있어야 한다.
- **방식은 외우지 말고** `orca skills get orchestration` 으로 버전 맞춤 가이드를 읽는다(플래그·서브커맨드가 릴리스마다 바뀐다). 요지:
  - `git worktree add` 로 만든 `.worktrees/*` 는 Orca 가 **인식하지 않는다**(실측). Orca 워커를 붙일 워크트리는
    `spawn`(= `orca worktree create`)으로 만든다(2절 「Orca 가 없을 때」).
  - **붙이기는 `worker-start` 가 에이전트까지 띄우게 한다** — `orca orchestration worker-start
    --task <id> --worktree id:<fullId> --agent claude --model <모델> --timeout-ms 180000`.
    **`terminal create` 로 먼저 띄우고 `terminal wait --for tui-idle` 뒤에 붙이지 마라** —
    갓 만든 터미널은 한동안 `agent_unconfigured` 로 거절당하고 `tui-idle` 은 그 게이트가
    아니다(2절 「붙이기 — 터미널을 직접 만들지 않는 이유」). `terminal create` 는 붙이지 않는
    터미널(빌드·로그 창)에만 쓴다.
  - **감독**이면 `orchestration task-create` + `dispatch --inject` + `check --wait --types worker_done,escalation,decision_gate`.
  - 주입 뒤에는 **반드시 `terminal read` 로 브리프가 제출됐는지 확인한다.** 아래 "브리프가 실제로 제출됐는지 확인하고 나서 대기한다" 참고.
- **감독(supervised) vs 완전 위임(handoff):** 완료를 기다려 리뷰·병합하면 supervised(`task-create` + `dispatch --inject` +
  `check --wait`). 소유권을 넘기고 안 지켜보면 full handoff(`terminal send` 또는 `worktree create --prompt`, lifecycle 프리앰블 안 붙임).
- **Orca 환경이 아니거나 오케스트레이션이 불가하면** 문서 첫머리의 폴백(superpowers 실행 경로)으로 가거나, 사용자에게
  워크트리 경로를 알려 직접 세션을 띄우게 한다.

### 역할별 모델 배정

`spawn` 의 두 번째 인자가 역할이고, 역할이 기본 모델을 정한다. `--model` 로 언제든 덮어쓴다.

| 역할 | 기본 모델 | 맡기는 일 |
|---|---|---|
| `implement` | **opus** | 설계 판단이 섞인 구현 |
| `review` | **opus** | 리뷰어. 판단이 곧 산출물이라 낮추지 않는다 |
| `verify` | **sonnet** | 정해진 검증을 실행하고 결과를 보고 (테스트·스모크·브라우저 확인) |
| `chore` | **sonnet** | 정해진 패턴의 기계적 일괄 변경, 문서 갱신 |

- `--model` 이나 `attach --terminal`(이미 도는 에이전트)이면 역할 기본값을 쓰지 않는다. `attach … review` 는
  `--terminal` 이 없으면 살아 있는 터미널이 있어도 새로 띄우므로 (`--model` 이 없을 때) 역할 기본값 opus 가 간다.
- 요약의 `모델:` 줄이 모델과 출처(`역할 기본값` 또는 `--model 재정의`)를 함께 보인다.

기본값을 두는 이유는 매번 고민하지 않게 하되 **예외는 명령줄에 명시로 남기기** 위해서다.
`--model` 이 붙어 있으면 "왜 기본과 다르게 골랐나"가 그 자리에 기록된다.

**모델 ID 대신 별칭(`opus`/`sonnet`)만 쓴다.** 별칭은 항상 그 계열의 최신 세대에 붙으므로
세대가 올라가도 스크립트와 이 문서를 고칠 필요가 없다. 모델 ID 를 박으면 다음 세대가 나온 날 전부 낡는다.

### 판단 지점은 "워크트리를 만들 때"가 아니라 "일을 시작할 때"다

워크트리만 만들어 놓고 메인 세션이 직접 작업하거나 Agent 도구를 써버리는 이탈이 실제로 일어나는 경로다.
위쪽 워크트리 생성 절차만 취하고 이 Orca 절을 지나친 경우다.

- 워크트리 **생성**은 `git worktree add` 로 해도 된다. 갈리는 지점은 **그 안에서 실제 작업을 시작하는 순간**이다.
- 그러므로 워크트리를 만들기 전에 `orca status --json` 을 실행한다. running runtime 이면 "메인 세션이 직접 작업"과
  "Agent 도구"는 선택지에서 빠진다.
- **워크트리를 만들었으면 이미 직접 처리 대상이 아니다.** 0절에서 직접 처리로 판단했다면 애초에 워크트리를 만들지 않는다.
  워크트리를 만들어 놓고 "이 정도는 간단하니 내가 하겠다"로 되돌아가는 것이 바로 이 이탈이다.

### 브리프가 실제로 제출됐는지 확인하고 나서 대기한다

**`worker-start` / `dispatch --inject` 가 성공을 반환해도 그것은 터미널에 바이트를 썼다는 뜻이지, TUI 가 그 입력을 제출했다는
뜻이 아니다.** 응답의 `stage: input_accepted` 나 `dispatch_input.state: accepted` 는 전송 성공까지만 보증한다. 브리프가
입력창에 텍스트로만 남고 실행되지 않은 채 방치되는 사고가 반복되는 자리다 — 워크트리 생성·세션 기동·브리프 입력까지 전부
정상인데 마지막 제출만 빠져서, 코디네이터는 `check --wait` 로 타임아웃까지 기다리고 워커는 아무것도 하지 않는다.

- **Why:** `worker-start` 는 터미널 생성과 브리프 주입을 한 번에 처리하므로 그 사이에 TUI 준비 대기가 없다. Claude Code TUI 가
  시작 화면을 그리는 중에 여러 줄 브리프가 들어가면 마지막 Enter 가 제출이 아니라 줄바꿈으로 흡수된다. 같은 명령이 어떤 때는
  되고 어떤 때는 안 되는 것도 이 때문이다 — 성공 여부가 타이밍에 달려 있어 반환값만 보고는 알 수 없다.
- **터미널 생성과 주입을 분리해서는 안 된다.** 갓 만든 터미널은 한동안 붙지 않아 `worker-start` 가 `agent_unconfigured` 로
  거절하고, `tui-idle` 통과는 그 게이트를 뜻하지 않는다(2절 「붙이기」). 미제출은 아래 `Ctx Used` 검증으로 막는다 —
  창을 벌려서 막는 것이 아니다.
  ```bash
  orca orchestration worker-start --task <task_id> --worktree id:<fullId> \
      --agent claude --model <모델> --timeout-ms 180000 --json
  ```
  이미 도는 에이전트에 붙일 때만 `--terminal <handle>` 을 쓰고, **그때는 `--worktree` 를 같이 줘야 한다** — 빼면
  코디네이터의 워크트리로 해석해 `terminal_worktree_mismatch` 로 실패한다. **`--model`·`--effort` 는 `--terminal` 과 함께 쓸 수 없다.**
- **검증 — 생략 금지.** 주입 직후 터미널을 읽어 제출됐는지 확인한다.
  ```bash
  orca terminal read --terminal <handle> --json
  ```
  입력창(`❯`)에 브리프 텍스트가 그대로 보이면 **미제출**이다. 다만 브리프가 길면 입력창이 화면을 채워 눈으로 구분하기 어렵다.
  **상태줄의 `Ctx Used` 가 확실한 판별 신호다 — `0.0%` 면 모델이 아직 한 번도 돌지 않았다는 뜻이니 미제출이다.** 엔터만 보내
  제출시킨다. **그 판별은 화면 전체가 아니라 상태줄 한 줄에서 해야 하고, 그 줄을 찾는 패턴에 보통 공백을 쓰면 맞지 않는다** —
  「상태줄은 화면 전체가 아니라 한 줄이다 — 앵커와 NBSP」 절.
  ```bash
  orca terminal send --terminal <handle> --text "" --enter --json
  ```
  다시 읽어 입력창이 비고 `Ctx Used` 가 0 보다 커졌는지 확인한 뒤에 대기로 넘어간다. 이 확인을 건너뛰면 방치 시간을
  타임아웃이 다 쓴 뒤에야 알게 된다.

### 워커를 띄웠으면 곧바로 수신 대기에 들어간다

제출을 확인했으면 **`scripts/orca-worker.sh wait`** 로 대기한다
(`orca orchestration check --wait --types worker_done,escalation,question` 을 감싼 것이다).

**타임아웃은 실패가 아니라 체크포인트다.** 긴 코딩 작업은 15~60분이 예사다.
스크립트는 이것을 종료코드로 가른다 — `0` 은 `worker_done` 수신, `3` 은 타임아웃, `1` 은 오류.
**exit 3 을 보고 워커가 죽었다고 판단하지 마라. 같은 명령을 다시 부르면 된다.**

**`wait` 은 받은 Delivery 를 `--ack` 로 확인 처리한다.** 이것을 빼면 Run 이 같은 배치를
계속 재생하므로(`orca orchestration check --help`: *"replays the same Delivery until `--ack`"*),
**먼저 끝난 워커의 보고가 다음 `wait` 에서 그대로 다시 나와 아직 도는 워커를 끝난 것으로 오인한다.**

워커가 `ask` 로 물어봐도 코디네이터가 수신하고 있지 않으면 **타임아웃(기본 15분)까지 방치되고**, 워커는 스스로 가정을
세워 진행하거나 멈춘다. 브리프 오류를 발견한 워커의 질문이 무응답으로 흘러 워커가 독자 판단으로 진행하는 것이 그 결과다.

코디네이터가 다른 일을 하느라 대기하지 못할 상황이면, 최소한 워커가 물어볼 만한 지점(브리프에 확신이 없는 값, 기존 코드와
충돌 가능성)을 디스패치 spec 에 미리 판단해 넣어 둔다.

## 4. 메인 세션과 워커의 역할 분리

**메인 세션은 디스패치·판정·병합만 한다. 실행은 전부 워커가 한다.** 이 절은 **워크트리로 간 작업에만** 적용된다 —
0절의 직접 처리 항목은 메인 세션이 그냥 고치고 커밋한다.

- **메인 세션이 하는 것:** 워크트리 생성과 초기 세팅, 워커·리뷰어를 띄우고 브리프를 쓰는 것, 받은 보고를 두고
  **무엇을 고치고 무엇을 이월할지 판정**하는 것, 병합과 워크트리 폐기, 최상위 문서(`.ruler/AGENTS.md`, `docs/*`) 갱신.
- **워커가 하는 것:** 구현, 리뷰, 테스트 실행(`pnpm test`·`pnpm typecheck`·`pnpm lint`·`pnpm fmt:check`, 하네스, 스모크),
  수정의 구분력 실증. **실행은 전부** 워크트리 안에서 워커가 하고 메인 세션은 결과를 보고로 받는다.

### "리뷰"는 리뷰어를 띄우는 것이지 메인 세션이 코드를 뜯어보는 것이 아니다

"지시·감독·리뷰·병합만 한다"의 "리뷰"는 **리뷰어 워커를 띄우는 것**이지 **메인 세션이 직접 diff 를 읽는 것**이 아니다.

- 워커의 보고가 미검증 주장인 것은 맞다. 그러나 **그 검증도 워커에게 시킨다.** 구현자와 리뷰어가 **각각 독립적으로**
  실증하므로 두 소스가 이미 교차 검증된 상태다.
- **제3의 워커를 띄우는 조건은 둘뿐이다** — 구현자와 리뷰어의 결론이 갈릴 때, 또는 한쪽이 "확인했는데 실패하지 않았다"고
  보고할 때. 그 외에 메인 세션이 세 번째 소스로 끼어드는 것은 잉여다.
- 메인 세션이 diff 를 여는 것은 **판정에 필요한 만큼**이다(어떤 파일이 바뀌었나, 보고 범위와 커밋 범위가 맞나).
  거기서 더 들어가 직접 재현·재실증하지 않는다.

### 예외 — 워커가 가질 수 없는 자원이 필요한 검증

터미널로 끝나는 검증은 전부 워커에게 시킨다. 예외는 **워커 환경에서 구할 수 없는 자원**이 필요할 때뿐이다.

- **브라우저 검증은 예외가 아니다.** 로컬 앱은 평문 HTTP 이고 MVP 인증은 로컬 토큰이라 워커가 자격증명을 입력할 일이
  없다. **브라우저 검증도 브리프에 넣어 워커에게 시킨다.** 어느 도구로 보는지는
  [브라우저 검증](browser-verification.md) 「도구를 고르는 순서」가 정한다.
- **남은 제약은 「브라우저를 누가 쥐는가」다.** 여러 세션이 동시에 쓸 때 탭과 브라우저 프로필 중 무엇이 갈리고 무엇이
  갈리지 않는지는 같은 문서 「여러 세션이 동시에 볼 때」가 갖는다. **브리프에는 "네가 연 탭은 네가 닫아라"를 넣는다.**
- **워커는 `/mcp` 를 못 누른다 — 브라우저는 워커를 띄우기 전에 떠 있어야 한다.** 세션이 시작될 때 꺼져 있었으면 그 워커는
  **수명 내내 브라우저를 못 보고 스스로 회복할 수단이 없다**(사람만 붙일 수 있는데, 워커에게는 사람을 부를 자리가 없다).
  그러면 **브라우저 검증을 못 한 채 나머지만 보고하고 끝난다.** `spawn` 의 `ensure_browser` 가 그래서 있다.
  두 고장이 어떻게 갈리는지는 같은 문서 「둘은 같은 고장이 아니다 — 언제 꺼져 있었는가로 갈린다」가 갖는다.
- **원격 Gateway·브리지가 필요한 검증은 자원이 하나뿐이다.** 플러그인은 브리지 주소 하나에만 붙고 디바이스 아이덴티티는
  워크트리마다 새로 생긴다(2절 「생성 직후 세팅」). 그 검증은 워커 하나에만 맡기고 병렬로 돌리지 않는다.
- 브라우저까지 가기 전의 자동 검증(타입 검사, 하네스 실행, 스크립트 스텁 실행 등)은 **여전히 전부 워커 몫이다.** 사람에게
  넘기는 것은 "봐야 판단이 서는" 화면 확인처럼 자동화로 대체할 수 없는 것만이다.
- **DB 확인은 예외가 아니다** — SQLite 파일은 워크트리 안 `data/` 에 있어 워커가 직접 연다.

### Why (둘 다 이유다)

1. **메인 세션의 셸은 작업 디렉터리가 유지된다.** 최상위와 `.worktrees/*` 를 오가다 보면 지금 어디에 있는지 착각하기 쉽고,
   최상위에서 워크트리용 명령을 돌리거나 그 반대가 된다. 메인 세션이 워크트리에 아무것도 쓰지 않으면 이 사고가 성립하지 않는다.
2. **워커가 도는 중에 메인 세션이 같은 파일을 만지면 워커의 작업을 덮어쓴다.** 겹치지 않는 것은 우연히 순차로 실행됐을 때뿐이다.

### 브리프에는 "됐다/안 됐다"가 아니라 진단을 요구한다

- "구분력이 있다/없다", "테스트 통과했다" 같은 결론만 받으면 원인 파악을 메인 세션이 다시 하게 되고, 그러면 위임한 의미가 없다.
- **무엇이 어떤 값으로 관찰됐고 원인이 무엇인지**까지 적게 한다. 예: "`allocateSeq` 가 같은 채널에 같은 seq 를 두 번 냈다 →
  최대값 조회가 삽입 트랜잭션 밖에서 돌아서".

### 수정의 구분력은 워커가 실증하고 복구한다

새로 쓴 테스트가 실제로 그 버그를 잡는지(구분력)는 **프로덕션 변경을 되돌려 테스트가 실패하는지** 확인해야 안다.
이것도 워커에게 시키고, 브리프에 아래를 명시한다.

- 프로덕션 코드를 되돌려 새 테스트가 **실제로 실패**하는지 확인한 뒤 **반드시 복구**한다.
- 마지막에 `git status` 로 작업 트리가 깨끗한지(변조가 남지 않았는지) 확인해 보고한다.
- **되돌렸는데도 실패하지 않으면 덮지 말고 그렇다고 보고한다.** 이 한 줄을 브리프에서 빼지 않는다 — 부정적 결과를 보고해도
  된다는 허용이 정직한 보고를 만든다.
- **되돌린 옛 코드가 바깥에 남기는 부작용을 먼저 본다.** 옛 코드가 고정 `/tmp` 경로나 홈 디렉터리 파일에 쓰면 되돌림 실증이 그 파일을 만든다 — 실증 전에 그 자리를 보고하고, 끝나면 내용을 확인한 뒤 지운다.
- **리뷰 워커의 변이는 작업 트리 소스를 잠시 고치는 일이라 권한 분류기가 막을 수 있다.** 막히면 다른 방법으로 다시 시도하지 않고
  코디네이터에게 묻는다(`orca orchestration ask`) — 우회하면 분류기가 막은 일을 다른 이름으로 하게 된다. 변이가 필수인 리뷰는 디스패치 전에
  사람이 그 워크트리의 편집 권한을 열어 둔다. 열지 못하면 브리프에 「변이가 막히면 정적 분석으로 대신하고 그렇다고 보고」를 적는다.

> **왜 코디네이터가 직접 재실증하지 않는가.** 브리프에 복구를 명시하면 워커도 작업 트리를 오염시키지 않고, 코디네이터의
> 재실증이 워커·리뷰어의 보고를 뒤집는 일은 거의 없다. 반면 코디네이터가 최상위와 워크트리를 착각하는 사고는 재실증 과정에서
> 난다. 옛 규칙("구분력은 코디네이터가 직접 실증하라")은 복구를 명시하지 않고 시켰다가 난 사고를 근거로 삼고 있었다.

### 시험을 갈아 끼운 줄은 옛 시험이 잡던 회귀를 새 시험이 아직 잡는지 잰다

리뷰어가 구분력을 볼 때, 시험을 시간 대신 값·문으로 바꾼 줄은 고침 자체가 아니라 **옛 시험의 잡는 범위**를 잰다 — 옛 시험이 잡던 회귀(그 값이 실제 동작에 닿는 고리)를 하나 골라 되돌리고, 새 시험과 옛 시험(`git show main:<시험 파일>`)이 각각 잡는지 본다. 리뷰 브리프의 「볼 것」에 이 줄을 넣는다.

- **Why:** 결정 배치 `server-ops-flakes`(2026-11-01)의 재접속 시험은 「dev:fake 가 백오프 상수를 `createApp` 에 넘긴다」까지만 값으로 쟀다. `app.ts` 가 그 값을 어댑터에 넘기는 줄을 지워도 새 시험은 통과했고 옛 시험은 잡았다 — 리뷰어가 이 변이로 찾아 고침 한 차례로 막았다.

### 흔들림 재현은 원래 단언이 다시 나오는지로 판정한다

흔들리는 시험을 재현할 때, 부하에서 다른 시험이나 같은 파일의 다른 시험까지 타임아웃으로 함께 깨지면 그것은 재현이 아니라 과부하다. 보고에는 반복 수·부하 조건(동시에 돈 것, load average)·나온 단언을 표로 남긴다.

- **Why:** 결정 배치 `server-ops-flakes`(2026-11-01)는 서버 시험 전체를 하나 더 겹쳐 load average 134 까지 갔는데도 대상 셋의 원래 단언이 세 부하 조건 34회에 한 번도 나오지 않았고, 대신 무관한 시험 10여 개가 타임아웃으로 흔들렸다. 타임아웃을 재현으로 세면 없는 원인을 고치게 된다.

이월 항목의 출처 보고서·리뷰는 `.superpowers/sdd/` 아래라 git 에서 빠져 워크트리에 없다. 브리프에 `/Users/jang2162/IdeaProjects/dodok.chat/.superpowers/sdd/<묶음>/` 절대 경로로 적는다.

### 이월 줄은 굵은 제목과 커밋을 붙인 번호로 가리킨다

이월 줄을 가리킬 때는 번호와 함께 **굵은 제목**을 적고, 번호에는 그 plan.md 의 커밋을 붙인다(예: `:608 @21ee36a`). 정리 배치는 보고에 옛 번호 ↔ 새 번호 표를 남긴다.

- **Why:** 줄이 지워지면 다음 분류의 번호가 다른 항목을 가리킨다. 이월 정리(2026-10-31) 뒤 옛 번호가 최대 50줄 밀렸고, 몇은 다른 항목과 같은 번호가 됐다(옛 :626 과 지금 :626 이 다른 줄).

### 나란히 쓰는 문서의 새 절은 조율자가 제목을 먼저 정해 준다

한 워커가 새 절을 쓰는 동안 다른 워커가 그 절을 가리켜야 하면, **조율자가 브리프에 그 절의 제목을 정해 두 워커에게 같이 준다.**

- **Why:** 가리키는 쪽 워커는 아직 없는 절의 제목을 알 수 없어 번호(「17절」)로 부르게 된다. 번호 인용은 인용 규칙(`docs/guideline/base/04-citation.md` 「문서를 가리킬 때는 절 제목으로」)을 어기고, 병합 뒤 조율자가 인용을 하나씩 찾아 제목으로 바꿔야 한다. 놓친 자리는 절이 하나 늘 때 조용히 다른 절을 가리킨다.
- **How to apply:** 브리프에 「새 절 제목: 「…」 — 쓰는 워커는 이 제목 그대로, 가리키는 워커는 이 제목으로」를 적는다. 날짜·결과 수처럼 쓰는 워커만 아는 값은 제목에 넣지 않는다.

### 브리프가 「스펙도 맞춘다」고 하면 — 스펙은 이력 문서다

스펙(`docs/superpowers/specs/*`)은 발행된 시점 기록이라 본문을 고치지 않는다(`docs/guideline/base/04-citation.md` 「이력 문서는 연대기 금지의 예외다」). 브리프에 「스펙·가이드도 맞춘다」를 쓸 때는 **스펙은 「구현과 맞춘 것」 장에 한 줄로 붙인다(장이 없으면 붙이지 않는다)**고 함께 적는다.

- **Why:** 두 규칙이 브리프 안에서 부딪치면 워커는 한쪽을 골라 멈추거나 묻는다 — 스펙 본문을 고쳐 쓰면 그때의 판단이 지금 값으로 덮여 거짓이 된다.

### 실연 브리프에는 결과를 쓸 자리를 적는다 — 결과는 리포트, 가이드는 절차

실연(실물 Gateway·러너·런 0회 하네스) 브리프에는 **결과는 `docs/superpowers/reports/<YYYY-MM-DD>-<주제>-live-smoke-report.md` 에 새로 쓰고, `docs/guides/live-smoke.md` 에는 지금도 참인 절차·함정만 올린다**고 적는다.

- **Why:** 날짜 붙은 결과를 가이드에 쌓으면 다음 사람이 그때의 관찰을 지금 절차로 읽는다 — 결과 절 안에만 있던 함정(플러그인 `dist` 정리·시크릿 개수의 WAL 함정 등)은 가이드에서 빠지고, 옛 설정 꼴의 하네스가 지금 것처럼 남는다.
- **How to apply:** 브리프의 보고 항목에 「가이드로 올린 절차·함정 목록」을 넣는다. 리포트 머리에는 무엇의 실연이었는지(계획·태스크)와 「지금 절차는 `docs/guides/live-smoke.md`」 한 줄을 둔다.

### 여러 배치가 같은 사용자 문서를 바꾸면 문서는 마지막 배치 하나로 모은다

코드 배치는 사용자 문서(`docs/manual/user-guide.md`·`docs/guides/agent-guide.md` 등)를 고치지 않고 보고에 「문서에 넣을 문장」(문서·절 제목·문장)을 적는다. 모든 코드 배치가 병합된 뒤 문서 배치(chore) 하나가 병합된 코드를 보며 한 번에 넣는다.

- **Why:** 같은 문서를 1차 배치 여럿이 고치면 겹침 검사가 막고, 순서로 풀면 배치가 사슬이 되어 병렬이 깨진다. 결정 배치(2026-10-31)는 다섯 배치가 `user-guide.md` 를 건드려야 해서 이렇게 풀었다.

### 워커는 목록을 바꿔친다 — **병합 전에 `git diff --name-only` 를 배치 목록과 대조하라**

브리프가 「이 파일들만 건드린다」로 경계를 그어도 **워커는 그 경계 밖 파일을 고치고 자기 파일 하나를 빼먹은 채 「목록대로
했다」고 보고할 수 있다.** 보고문은 브리프를 그대로 되읊으므로 **보고만 읽어서는 드러나지 않는다.**

- **판정 전에 메인 세션이 `git diff --name-only <기준>..<워커브랜치>` 를 돌려 브리프의 파일 목록과 양방향으로 대조한다** —
  목록에 없는데 바뀐 것, 목록에 있는데 안 바뀐 것 **둘 다** 본다.
- 어긋나면 **병합하지 말고 워커에게 되돌려라.** 메인 세션이 대신 고치면 「누가 무엇을 했는가」가 섞여 다음 배치의 경계도 무너진다.
- 배치를 여럿 병렬로 돌릴 때는 이 대조가 **충돌을 병합 전에 잡는 유일한 자리**다.

### 붙이기가 `turn_start_unobserved`·「supervised 로 붙지 못했다」로 끝나면 브리프가 안 들어갔다

`spawn`·`attach` 가 `turn_start_unobserved` 나 「supervised 로 붙지 못했다」로 끝나면 워커 터미널은 브리프 없이 빈 프롬프트로 남는다. `wait` 는 그 끝을 받지 못한다(2절 「붙지 못한 워커는 `wait` 로 잡히지 않는다」).

- **How to apply:** 터미널 화면을 읽어(`orca terminal read --terminal <핸들> --screen --json`) 빈 프롬프트인지 본다. 그렇다면 그 터미널을 닫고 다시 `attach` 하거나, `orca terminal send` 로 브리프 경로를 넣고 보고 파일이 생기는지로 끝을 잰다.
- **Why:** 조율자가 결정 배치(2026-11-01)에서 두 번 겪었다(`followups`·`server-ops-flakes`). 붙이기가 실패를 알려도 터미널은 살아 있어, 화면을 보지 않으면 워커가 도는 줄 알고 기다린다.

## 5. 커밋 주의

최상위 체크아웃은 다른 작업·사람이 동시에 만지고 있을 수 있다. 워크트리 안에서도 워커가 여럿이면 같은 문제가 생긴다.

- `git add -A` / `git commit -a` 로 **작업 트리 전체를 쓸어 담지 않는다.** 남의 작업 중인 파일이 내 커밋에 섞인다.
- 커밋할 파일을 **경로로 명시**해서 stage 한다.
- 커밋 직전에 `git status` 로 stage 목록을 확인한다. 내가 건드리지 않은 파일이 있으면 멈추고 사용자에게 알린다.
- 커밋 전에 `pnpm lint` 와 `pnpm fmt:check` 를 통과시킨다. 포맷은 `pnpm fmt` 로 맞춘다 — 손으로 맞추지 않는다.

## 6. 워크트리 폐기

### 먼저 — 현황과 정리는 `status` / `reap` 이 한다

```bash
scripts/orca-worker.sh status                 # 워크트리마다 다음 행동까지 찍는다
scripts/orca-worker.sh reap <슬러그>           # 하나 정리
scripts/orca-worker.sh reap --all-merged      # 병합된 것만 일괄 정리
scripts/orca-worker.sh reap --all-merged --dry-run   # 무엇이 지워질지 먼저 본다
scripts/orca-worker.sh stop <슬러그>           # 끝난 워커 회수 뒤 그 워크트리의 터미널만 정지(워크트리는 그대로)
scripts/orca-worker.sh stop --all --dry-run   # 무엇이 정지될지 먼저 본다
```

`status` 는 **미정리가 하나라도 있으면 exit 1**, 없으면 exit 0 이다.
`.claude/hooks/orca-worker-check.sh` 가 세션 시작과 매 프롬프트마다 이 종료코드만 보고 세션에 현황을 알린다
(`.claude/settings.json` 의 `SessionStart`·`UserPromptSubmit` 훅). "미정리"는 둘뿐이다 — **워커가 `done` 인데 터미널이
살아 있는 것**과 **기준 브랜치에 병합됐는데 워크트리가 남아 있는 것.** 도는 워커는 미정리가 아니고, `.orca-keep` 으로
보호한 워크트리(`keep`)도 아니다.

**`reap` 은 지우기 전에 두 관문을 통과시킨다. 하나라도 걸리면 거부한다.**

1. `git merge-base --is-ancestor <워크트리브랜치> <기준브랜치>` — 미병합 커밋이 있으면 거부
2. `git -C <워크트리> status --porcelain` — 미커밋 변경이 있으면 거부

기준 브랜치는 `--base` 로 받고 기본값은 지금 세션의 현재 브랜치다. 기준이 틀리면 게이트는
**덜 지우는 쪽으로** 틀린다(미병합으로 보여 거부) — 안전한 방향으로 실패한다.
`--force` 로만 우회할 수 있고, 우회할 때는 **무엇을 버리는지 목록을 먼저 출력한다.**
**`--all-merged` 와 `--force` 는 함께 쓸 수 없다** — 한 명령이 저장소의 모든 워크트리에서
미병합 커밋과 미커밋 파일을 확인 절차 없이 버리게 된다. 먼저 `--all-merged --dry-run` 으로
보고, 버릴 것을 정했으면 슬러그를 하나씩 지정해 `--force` 한다.

> **두 번째 관문이 왜 필요한가.** 브랜치는 `main` 에 병합됐는데 그 뒤에 손댄 파일이 미커밋으로 남아 있는 워크트리가
> 생긴다. 병합 여부만 보고 일괄 정리하면 그 작업이 사라진다.

### 쓰는 중인 워크트리는 `keep` 으로 보호한다

```bash
scripts/orca-worker.sh keep <슬러그>            # 보호
scripts/orca-worker.sh keep <슬러그> --remove   # 해제
```

워크트리에 `.orca-keep` 마커가 생기고, `status` 가 그것을 **다른 무엇보다 먼저** 보아
`keep` 으로 분류한다. `keep` 은 미정리로 세지 않으므로 **훅이 조용해지고**,
`reap` 은 `--all-merged` 에서 건너뛰며 슬러그를 직접 지정해도 거부한다.
**`--force` 로도 뚫리지 않는다** — 먼저 `--remove` 로 해제해야 한다.

> **왜 두 관문으로 부족한가.** 위 두 관문은 **git 이 아는 것**만 본다. 커밋이 전부 `main` 에 들어가 있고 미커밋도 0이지만
> 사람이 계속 쓰는 작업 환경인 워크트리가 있다. 관문을 통과해 `reap --all-merged` 가 지우면 코드 손실은 없어도 체크아웃과
> 터미널이 사라져 다시 만들어야 한다. **「병합됐고 미커밋 없음」은 「다 썼다」가 아니다.** 그 판단은 사람만 할 수 있고,
> `keep` 이 그 판단을 적어 두는 자리다.

**`status` 와 `reap` 은 Orca 가 모르는 고아 디렉터리도 다룬다.** 이미 제거된 워크트리의
껍데기(`node_modules`·`.turbo`·`dist` 만 남은 디렉터리)는 `git worktree list` 에도
`orca worktree ps` 에도 없어서 열거되지 않는다. 스크립트는 `orphan` 토큰으로 보고하고 `reap <슬러그>` 로 치운다 —
내용이 의존성·빌드 산출물뿐일 때만 지우고, 아니면 목록을 내고 거부한다.

**잔해 디렉터리에도 터미널이 붙어 있을 수 있다.** 워크트리 등록이 사라져도 그 디렉터리에서
돌던 터미널은 남는다. Orca 의 워크트리 목록에 없으니 `liveTerminalCount` 로는 세지지 않고,
**전역 터미널 목록을 경로로 세어야만 보인다.** 하나라도 붙어 있으면 `status` 는 `orphan-live`
로 보고하고 `reap` 은 `--force` 로도 지우지 않는다 — 워크트리 쪽 `waiting` 과 같은 취급이다.
**여기서 세지 못한 것을 0으로 넘기면 워커가 도는 작업 디렉터리가 통째로 `rm -rf` 된다.**
그래서 셀 수 없을 때도 「붙어 있다」로 친다. 심볼릭 링크를 사이에 둔 두 표기가 같은 디렉터리를
가리키므로 **양쪽을 실물 경로로 맞춘 뒤 비교한다** — 글자만 비교하면 같은 디렉터리를 다른
것으로 보고 0을 내고, 그 0이 곧 삭제 허가가 된다.

`reap` 의 실행 순서는 **회수 → 터미널 정지 → 폐기 → 잔해 제거**다. 터미널이 살아 있으면
`worktree rm` 이 실패하므로 순서가 곧 요구사항이다. 마지막 잔해 제거(`git worktree list` 에
없는 껍데기 디렉터리 + `git worktree prune`)가 빠지면 `.worktrees/` 에 껍데기가 쌓인다.
**`reap` 은 자기가 서 있는 워크트리를 건너뛴다** — 워크트리 안의 워커가 `--all-merged` 를
돌리는 일이 실제로 생기고, 가드가 없으면 자기 발밑이 무너진다.

**회수 단계가 무엇을 거르는가가 이 순서의 안전을 정한다.** `orca orchestration worker-list` 에는
**저장소 경계가 없어** 모든 프로젝트의 워커가 한 목록에 들어 있고(범위는 Run 이지 저장소가 아니다),
항목에는 `worktreeId` 라는 최상위 필드가 **없다.** 그래서 이 워크트리 것임을 증명하는 길은 둘뿐이고 둘 다 정확 일치다 —
`.resource.worktreeId` 가 같거나, `.agentTerminalHandle` 이
`orca terminal list --worktree <셀렉터>` 가 낸 핸들 집합에 있거나.
`.resource` 는 워커가 쥔 워크트리 자원 기록이라 **터미널이 이미 죽은 뒤에도 남고**,
회수해야 할 것이 정확히 그것이다. **어느 쪽도 대지 못하는 dispatch 는 건너뛰고 그렇다고
출력한다.** 없는 필드로 거르면 항상 0건이 되어 회수가 조용히 생략되고, 느슨하게 거르면
남의 프로젝트 워커를 회수한다 — **둘 다 종료코드로는 성공으로 보인다.**

**목록은 끝까지, 모든 Run 에서 읽는다.** `worker-list` 는 `--run` 이 없으면 부른 터미널에 묶인 Run 만
내고, 묶인 Run 이 없을 때만 모든 Run 을 낸다. 한 번에 최신 100행만 내므로 나머지는
`page.nextCursor` 로 이어 받는다 — 첫 페이지만 읽으면 오래된 dispatch 와 다른 Run 의 dispatch 는
「증명된 dispatch 없음」으로 보인다. 그래서 회수는 `--cursor` 로 끝 페이지까지 읽고, 응답의
`scope.source` 가 `all` 이 아니면(`spawn` 이 Run 을 묶은 조율자 터미널이 그렇다) `run-list` 의 Run 을
하나씩 `--run` 으로 읽는다. 「모든 Run」을 고르는 옵션은 `worker-list --help` 에 없어서, 묶인
터미널에서는 Run 수만큼 왕복하고 `run-list` 에 없는 Run 은 보지 못한다. 한 장이라도 못 읽거나,
이미 받은 커서가 다시 오거나, 장 수가 `ORCA_WORKER_MAX_PAGES`(기본 1000)에 닿았는데 아직 남았으면
「목록을 읽지 못했다」로 치고 **아무것도 회수하지 않는다** — 덜 읽은 목록의 「0건」은 다 읽은
「0건」과 구별되지 않는다.
**묶인 터미널에서는 Run 이 백 개를 넘으면 한 번 읽는 데 수십 초가 든다** — Bash 도구로 부를 때는
타임아웃을 넉넉히 준다(왕복 수는 `orca orchestration run-list --json` 을 끝 장까지 센 Run 수다).
그래서 한 명령은 목록을 한 번만 읽는다. `reap --all-merged`·`stop --all` 은 처음 회수할 때 읽은
목록(과 못 읽었다는 사실)을 다음 워크트리에 돌려 쓰고 — 한 워크트리의 회수는 다른 워크트리의 행을
바꾸지 않는다 — `attach` 는 Task 를 만들기 전에 한 번 읽어 진행 중 검사와 `--retry-of` 가 함께 쓴다. 목록을 못 읽어도 닫기는 그대로 간다(`reap` 은 폐기까지) — 그 워크트리 워커의 터미널 꼬리는 보관되지 않는다(「터미널을 끄는 것은 `stop` 이 한다」 절). 일괄 모드는 못 읽었다는 사실도 돌려 쓰므로, 한 번만 실패해도 남은 워크트리 전부가 회수 없이 닫힌다.

**소유 증명과 회수 대상 판정은 다른 일이다.** 증명은 「이 워크트리 것인가」를 묻고, 판정은
「부르면 무엇이 닫히는가」를 묻는다. 증명 단계에서 상태로 걸러 버리면 건너뛴 것과 그 이유를
조율자가 볼 방법이 없어진다 — 그래서 증명은 전부 통과시키고 판정이 뒤에 온다.

### 회수는 `reclaimable` 만 부른다 — 「회수 N건」이 사실이어야 한다

판정은 `worker-list` 항목의 **`terminalState`** 로 한다. 그것이 런타임 자신의 회수 회계
어휘다 — `worker-list --help` 의 `--terminal-state` 가 받는 값이 그대로이고, 응답의
`.result.counts` 도 이 값으로 집계된다.

| `terminalState` | 부르는가 | 왜 |
|---|---|---|
| `reclaimable` | **부른다** | 우리가 쥐었고 아직 회수하지 않은 settled 워커다 |
| `released` | 안 부른다 | 이미 끝났다. `--help`: *repeating the call reports `already_released`* |
| `retained` | 안 부른다 | 서버가 거절한다. `--help`: *Never closes … user-taken-over terminals, or unproven identities* |
| `active` | 안 부른다 | settled 가 아니다. `worker-release` 는 *post-completion cleanup for a settled worker* 다 |
| `release_pending`·`release_unknown`·모르는 값 | 안 부른다 | 판정할 수 없다 — **fail closed** |

**`retained` 와 `released` 에 `worker-release` 를 불러도 아무 프로세스도 닫히지 않는다.**
그런데 종료코드는 0이라, 부른 횟수를 그대로 세면 **아무것도 회수하지 않고도 「회수 N건」이
찍힌다.** 다음 사람은 그것을 「회수됐구나」로 읽는다. 그래서 출력은 회수한 것과, 건너뛴 것과
그 이유(이미 회수됨 / 사용자가 넘겨받음 / 자원 기록 없음 / 판정 불가)와, 실패한 것을 나눠 센다.

**`active` 를 거르는 것은 안전 장치다.** 그것은 지금 돌고 있는 워커이고, 자기 자신일 수도 있다.

`release_pending`·`release_unknown` 은 `--help` 의 열거값에서만 왔다. 그래서 부르지 않는다 — **모르면 부르지 않는다.**
`worker-list` 에는 저장소 경계가 없어, 여기서 한 번 느슨해지면 그 대상이 남의 프로젝트가 된다.

### 터미널을 끄는 것은 `stop` 이 한다 — `terminal list` 평문을 grep 하지 마라

`reap` 은 터미널이 살아 있는 워크트리를 일부러 거부한다. 그래서 폐기 전에 터미널을 먼저
끄게 되는데, **그 자리에서 핸들을 손으로 모으려고 하면 남의 것을 끈다.**

```bash
scripts/orca-worker.sh stop <슬러그>           # 끝난 워커를 회수하고 그 워크트리의 터미널만 정지
scripts/orca-worker.sh stop --all              # 이 저장소의 워크트리 전부(도는 워커는 건너뛴다)
scripts/orca-worker.sh stop --all --dry-run    # 무엇이 정지될지 먼저 본다
scripts/orca-worker.sh stop <슬러그> --force   # 도는 워커도 끊는다 — 슬러그를 찍을 때만
```

**끝난 워커(`done`)는 `--force` 없이 꺼진다.** `stop` 이 「워커가 도는 중이다」로 거부하면 그것이
신호다 — 터미널을 읽어 확인한 뒤에만 `--force` 를 붙인다. 흐름 안에서 `--force` 를 미리 붙여 두면 그
거부가 막던 사고(도는 워커의 문맥을 끊는 것)가 그대로 난다.

`stop` 은 **이 저장소의 `repoId` 로 거른 워크트리에만** 나가고, 파괴 명령은 정확 일치
셀렉터를 받는 `orca terminal close --worktree "id:<repoId>::<path>" --all` 하나뿐이다.
`.orca-keep` 보호는 여기서도 `--force` 로 뚫리지 않고, **자기가 서 있는 워크트리는 끄지
않는다.** 저장소 밖 슬러그는 셀렉터조차 만들지 않고 실패로 끝낸다.

`stop` 은 프로세스만 멈추지 않고 그 워크트리의 터미널 탭·레이아웃·재개 기록까지 지운다
(`terminal close --all` — 여기 `--all` 은 「그 워크트리의 터미널 전부」다. `stop --all` 의
「이 저장소의 워크트리 전부」와 다르다). 끈 뒤에는 그 터미널을 `terminal read` 로 읽을 수 없고,
`worker-release` 도 터미널을 찾지 못해 터미널 꼬리 보관 없이 회수하거나 `release_unknown` 으로 남긴다.
그래서 **`stop` 도 `reap` 처럼 닫기 전에 회수한다** — 그 워크트리의 워커를 「회수는 `reclaimable` 만
부른다」 절의 판정대로 `worker-release` 한 뒤에 닫는다. 「워커가 도는 중이다」 거부는 회수보다 앞서고,
도는 워커(`active`)는 회수하지 않으므로 `--force` 로 끊을 때도 터미널만 닫힌다. 그렇게 끊긴 워커는
프로세스가 끝나면서 런타임이 실패로 정산해 `reclaimable` 이 되고, 나중 `reap` 이 회수를 부르지만
터미널이 이미 없어 꼬리를 보관하지 못한 채 `released` 가 되거나 `release_unknown` 경고를 낸다 —
`--force` 가 버리는 것에는 그 워커의 출력 보관도 들어간다. 회수 실패는 경고만 내고
`stop` 의 종료 코드를 바꾸지 않는다(`reap` 과 같다). 나중 `reap` 은 이미 `released` 인 워커에
`worker-release` 를 다시 부르지 않는다.

`stop` 의 exit 1 은 「워커가 도는 중이다」 거부만이 아니다 — `경고: terminal close 실패`, 보호된
워크트리, 이 저장소에 없는 슬러그도 1 이다. **`wait` 로 끝을 기다릴 것은 「워커가 도는 중이다」일
때뿐이다.** close 실패는 스크립트가 출력을 버려 이유가 남지 않으니
`orca terminal close --worktree "id:<repoId>::<path>" --all --json` 을 한 번 불러 `error.code` 를 본다.

**`--all` 과 `--force` 는 함께 쓸 수 없다.** `--force` 는 「도는 워커를 끊어라」는 뜻이고
`--all` 과 합치면 **이 저장소의 워커를 한 번에 전부 끊고 exit 0** 이 된다 — 코드는 남지만
진행 중인 워커의 문맥은 전부 사라지고, 출력만 보고는 무엇을 끊었는지 알 수 없다.
`reap` 의 `--all-merged --force` 금지와 같은 관문이다. 먼저 `--all --dry-run` 으로 보고,
끊을 것을 정했으면 슬러그를 하나씩 지정해 `--force` 한다.

**`orca terminal list` 의 평문을 grep 으로 파싱하지 마라. 둘이 동시에 어긋난다.**

- **그 목록은 머신 전역이다.** 저장소 경계가 없어 다른 프로젝트의 터미널이 같은 목록에 섞인다.
- **한 항목이 여러 줄이고 길이가 가변이다**(핸들 줄 + `preview:` + 가변 길이 미리보기 + 빈 줄).
  `grep -B`/`-A` 로 창을 잡으면 그 창이 **앞뒤 항목을 통째로 삼키고** 삼킨 항목의 핸들까지
  딸려 나온다. 미리보기 길이가 화면 내용에 따라 달라지므로 **맞는 창 크기 자체가 없다.**

**그렇게 만든 루프는 조용히 성공한다.** 껐다는 것만 알고 무엇을 껐는지는 모른다 — 끈 것이
다른 프로젝트의 워커든 자기 자신의 세션이든 출력이 같고, 전부를 끄는 것이 아니라 창에 걸린
**연속 구간**만 끄므로 일부가 살아남아 「내 필터가 들었다」로 읽힌다.

핸들이 꼭 필요하면 **평문이 아니라 범위를 좁힌 JSON** 에서 꺼낸다.

```bash
orca terminal list --worktree "id:<repoId>::<path>" --json | jq -r '.result.terminals[].handle'
```

`id:` 셀렉터는 **정확 일치**로 해석된다. 없는 경로를 주면 **0건**이고, 실패했다고 해서
`active`/`current` 처럼 넓은 것으로 **물러나지 않는다.**

> ⚠ **함정은 빈 셀렉터다.** `--worktree ""` 는 오류가 아니라 **전역 목록을 그대로 낸다** —
> 셀렉터를 준 줄 알고 부른 사람이 머신의 모든 터미널을 받는다. 셀렉터를 변수로 조립할 때
> 그 변수가 비면 범위가 조용히 전역으로 넓어진다는 뜻이다.
> `--worktree "id:"`(값 없는 `id:`)는 `selector_not_found` 로 **실패**하고,
> `--worktree "id:<없는repo>::<없는경로>"` 는 **0건**이다.
> 스크립트가 이 자리에 닿지 않는 이유는 **모든 호출에 `id:` 접두사를 리터럴로 붙이고**
> 셀렉터를 만들기 전에 `repo_id` 가 비면 멈추기 때문이다.

이 응답에는 `worktreeId` 와 `worktreePath` 가 함께 실리는데 **`worktreePath` 는 비어 있는
항목이 있다.** 경로로 판정할 때는 `worktreeId` 의 `<repoId>::<path>` 꼬리를 대안으로 함께 봐야 한다.

### 수동 절차 (Orca 가 없을 때·스크립트를 검증할 때)

작업이 병합되거나 폐기되면 정리한다. **폐기 전에 그 브랜치의 커밋이 전부 병합됐는지 먼저 확인한다** —
마지막 정리 커밋이 병합 뒤에 붙는 일이 있다.

```bash
git merge-base --is-ancestor <워크트리브랜치> main && echo "전부 병합됨" || echo "안 들어간 커밋이 있다"
```

**Orca 가 만든(또는 인식한) 워크트리는 Orca 로 지운다** — git 으로만 지우면 Orca 메타데이터에 유령 항목이 남는다.

```bash
orca worktree rm --worktree id:<fullId> --json
```

Orca 가 없거나 인식하지 않는 워크트리는 git 으로 지운다.

```bash
git worktree remove .worktrees/dodok.chat/<슬러그>
```

디렉터리를 `rm -rf` 로 먼저 지웠다면 `git worktree prune` 을 함께 돌려 등록 정보를 지운다.

**어느 쪽이든 그 워크트리에 붙은 Orca 터미널을 먼저 종료한다.** 핸들을 하나씩 찾지 말고
**저장소 범위 셀렉터로** 끈다 — 핸들 기준으로 가면 그 핸들을 어디서 얻을지가 문제가 되고,
그 자리에서 짜는 `orca terminal list | grep` 이 다른 프로젝트의 터미널과 자기 터미널까지 끈다
(→ 「터미널을 끄는 것은 `stop` 이 한다」 절). 워커가 붙어 있던 워크트리면 닫기 전에
`worker-release` 로 회수한다 — 닫은 뒤에는 회수가 그 터미널을 찾지 못한다(같은 절).

```bash
orca terminal close --worktree "id:<repoId>::<path>" --all
```
