# 에이전트 DM Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> 이 저장소에서는 Orca 워커가 태스크를 맡는다(`AGENTS.md` 「작업 방식」). 태스크 하나 = 워크트리 하나 = 브리프 하나. 태스크마다 main 에 병합해도 초록이어야 한다.

**Goal:** 등록된 에이전트와 채널 없이 1:1 로 대화한다. DM 은 세션 단위로 쌓이고, 주인 말고는 owner·admin 도 화면·API·검색·알림·운영 표 어디에서도 볼 수 없다.

**Architecture:** DM 은 `channels.kind = 'dm'` 인 채널이다(주인 사람 하나 + 에이전트 하나, (주인, 에이전트)마다 하나) — 메시지·세션·첨부·카드·런·검색·읽지 않음·푸시는 채널 세션(스펙 A)의 것을 그대로 쓴다. 지금은 채널마다 접근 판정이 없으므로 **먼저 접근 경계(`canReadChannel` + SQL 거름)를 모든 진입점에 깔고**(태스크 1·2 — 아직 DM 을 만들 길이 없다), 그다음 DM 을 만들고 쓰는 길을 연다(태스크 3~5). 남의 DM 은 404 — 있는지조차 드러내지 않는다.

**Tech Stack:** Fastify 5 · Socket.IO 4.8 · drizzle-orm 0.45 + better-sqlite3 · zod 4 · React 19 + TanStack Router/Query · OpenClaw 2026.9.4 플러그인 SDK · Claude Agent SDK(러너). **새 의존성 없음.**

**Spec:** `docs/superpowers/specs/2026-10-25-agent-dm-design.md` — 결정 0장, 범위 1장, 데이터 2장, 동작 3장, 접근 판정 4장, 오류 5장, 검증 6장, 완료 기준 7장. 그 아래 채널 세션 스펙 `docs/superpowers/specs/2026-10-25-channel-sessions-design.md` — **11장 「구현과 맞춘 것」이 지금 코드다**(본문과 다르면 11장). 로드맵 `docs/superpowers/specs/2026-10-25-sessions-dm-runner-roadmap.md` 결정 3. **태스크를 시작하기 전에 스펙의 해당 장을 읽는다.**

## Global Constraints

- DM 판정은 서버 `apps/server/src/auth/channel-access.ts` 한 파일: `canReadChannel`(행 하나)·`readableChannelSql`(목록 SQL)·`assertChannelReadable`(404). 채널·대화·메시지·런·승인·첨부를 내보내거나 바꾸는 모든 경로가 지난다. **접근 판정이 역할 판정(403)보다 먼저다** — 남의 DM 에 역할 정책이 403 을 내면 있다는 것이 드러난다. 역할 정책이 `requirePolicy` preHandler 에 있는 경로는 preHandler 를 `requireSession` 으로 바꾸고 핸들러에서 접근 판정 다음에 정책을 부른다(태스크 1 판단 2). 대화·런 id 로 닿는 자리는 조회 WHERE 에 `readableChannelSql` 를 붙인 도우미(`conversations/store.ts getReadableConversation`·`runs/store.ts getRunInWorkspace` 의 `readerId`)로 같은 404 를 낸다(태스크 1 판단 1).
- 남의 DM → HTTP 404 `NOT_FOUND`, wire 는 같은 코드의 ack. id 로 무언가를 찾는 경로는 「없음」과 「남의 DM 의 것」이 같은 코드·같은 문구여야 하고, 역할 갈래·VALIDATION 갈래보다 그 판정이 먼저다(태스크 1 리뷰 L1 `approval.resolve`·L2 `message.send` 의 `conversationId`). 채널 관리 경로를 DM 에 → `VALIDATION`(주인에게만 — 남은 404 가 먼저). 읽기 전용 DM 에 쓰기 → 409 `DM_READ_ONLY`(새 코드).
- 데이터: `channels.kind` `'channel' | 'dm'`(NOT NULL, 기본 `'channel'`), `dm_owner_id`(users, nullable FK)·`dm_agent_id`(agents, nullable FK), 유일 `channels_dm_pair (dm_owner_id, dm_agent_id) WHERE kind = 'dm'`. `agents.dm_access` `'off' | 'admins' | 'everyone'`(NOT NULL, 기본 `'admins'`). 마이그레이션 하나(`0029_*`), `pnpm -F @dodok/server db:generate` 로 만들고 다시 generate 해 「No schema changes」.
- DM 채널 행: `name` = `dm`(내부용 — 화면은 에이전트 이름), `visibility` `private`, `relay_policy` 기본값(쓰지 않음), `session_policy` `{ create: "members" }`(접근 판정이 주인만 들인다), `created_by` = 주인. `channel_members` 는 주인 사람 행(`role: "member"`) + 에이전트 행(`autoRespond: true`) 둘뿐.
- `dmAccess` 판정: `off` 는 아무도, `admins` 는 admin 이상, `everyone` 은 모든 활성 멤버. 에이전트가 보관·꺼짐이면 판정과 무관하게 새 DM 을 만들 수 없다.
- 문구(합쇼체, 그대로):
  - 사이드바 절 「다이렉트 메시지」, 고르기 대화상자 제목 「DM 할 에이전트」, 에이전트 카드·설정 버튼 「DM 보내기」.
  - 에이전트 헤더 줄 `다이렉트 메시지: @<주인 핸들> 님과 1:1`(shared `formatDmLine` 하나 — 조사를 「님과」로 고정해 받침 판정이 없다, PD8).
  - 읽기 전용 사유: `agent_archived` 「보관된 에이전트라 읽기만 할 수 있습니다」 · `agent_disabled` 「꺼진 에이전트라 읽기만 할 수 있습니다」 · `dm_not_allowed` 「이 에이전트와의 DM 이 허용되지 않아 읽기만 할 수 있습니다」.
  - DM 첫 안내(세션이 하나도 없을 때 빈 화면): 「이 DM 은 나만 봅니다. 다만 에이전트는 자기 기억(메모리·작업 디렉터리의 파일)을 거쳐 여기서 들은 것을 다른 채널의 답에 쓸 수 있습니다 — dodok 은 이것을 막지 못합니다.」
  - DM 지시 칸 이름 「이 DM 의 지시」.
  - `dmAccess` 선택지 「끔」·「admin 이상」·「모두」, 「모두」 아래 설명 「member 도 이 에이전트와 DM 을 열고, 그 DM 의 도구 승인을 스스로 결정합니다.」
  - 푸시 제목 `@<에이전트 핸들> <이/가> 답했습니다`(서버 `util/josa.ts`), 운영 런 표의 DM 묶음 줄 이름 「DM」.
- 권한은 서버가 요청마다 판정한다(웹이 숨기는 것은 편의). 새 경로는 `apps/server/test/roles.matrix.test.ts` 와 팀 스펙(`docs/superpowers/specs/2026-09-26-team-members-design.md`) 「역할과 권한」 표에 더한다.
- 외부 입력은 경계에서 Zod 파싱. shared 는 Node 전용 API 금지. 레이트리밋 숫자는 `apps/server/src/modules/ops/limits.ts` 한곳(새 숫자 없음 — DM REST 는 기존 사용자 버킷).
- 포트 5173·3000 금지(사용자 인스턴스 3100·5180 도 건드리지 않는다 — 워커는 브리프가 주는 포트). 프로세스는 자기 PID 로만, `pkill` 금지. **모델 런 없음.**
- 커밋: `git add -A`·`git commit -a` 금지, 경로 명시. Conventional Commits + 스코프. 워커 트레일러 `Co-Authored-By: <네 실제 모델명> <noreply@anthropic.com>`.
- 문서·주석을 쓰기 전에 `docs/guideline/base/03-comments.md`·`04-citation.md` 를 읽는다.
- 끝내기 검사: 루트 `pnpm test`(**다른 검사와 동시에 돌리지 않는다**) → `pnpm typecheck && pnpm lint && pnpm fmt:check`, 각 exit code, 테스트 수는 자기 실행 출력에서 패키지별로(0개는 통과가 아니다). 웹을 바꿨으면 `pnpm -F @dodok/web build`, 서버를 바꿨으면 `pnpm -F @dodok/server build && pnpm -F @dodok/server bundle:smoke`, 플러그인을 바꿨으면 `pnpm -F @dodok/openclaw-plugin build`.

## 계획 판정 (스펙과 맞춘 것)

조사한 코드에 맞춰 스펙을 구체화한 것. 태스크 7 이 스펙에 「구현과 맞춘 것」 장을 만들어 옮긴다.

- **PD1 — DM 채널은 열 때 만든다(스펙 3.1 의 「첫 보내기가 만든다」와 다르다).** `POST /api/v1/dms { agentId }` 가 (주인, 에이전트) DM 채널을 찾거나 만든다(유일 인덱스 + `onConflictDoNothing` 뒤 다시 읽기 — 동시 두 요청도 행 하나). 대화는 만들지 않는다 — 첫 보내기는 지금 `message.send { channelId, newConversation }` 그대로다. `MessageSend` 계약을 바꾸지 않으려는 것이고, 빈 DM 채널 행은 메시지가 없어 해가 없다. 사이드바는 `lastSeq > 0` 인 DM 과 지금 연 DM 만 보인다. 이미 있는 DM 은 허용 검사 없이 돌려준다(읽기 전용이어도 — 403 은 새로 만들 때만). `findOrCreateDm` 의 `onConflictDoNothing` + 다시 읽기는 여러 프로세스가 같은 DB 를 쓸 때의 방어선이다 — better-sqlite3 는 동기라 한 프로세스 안의 동시 요청은 앞선 찾기가 받는다(태스크 3).
- **PD2 — DM 화면은 채널 경로를 쓴다.** `/dm/$agentId` 는 `POST /dms` 로 채널 id 를 받아 `/c/<DM 채널 id>` 로 넘기고(그 뒤는 채널 세션의 「최근 세션으로 넘김」), 채널 레이아웃이 `channel.kind === "dm"` 이면 DM 꼴(머리·세션 목록 날짜 묶음·설정 칸 없음·스레드 없음)로 그린다. 세션 목록·작성기·타임라인 컴포넌트는 그대로.
- **PD3 — 웹의 채널 목록과 DM 목록은 나뉜다.** REST `GET /api/v1/channels` 는 `kind = 'channel'` 만, 내 DM 은 `GET /api/v1/dms`(에이전트·`lastMessageAt`·`readOnlyReason`, 최근 활동순). 제어 도구의 「읽을 수 있는 채널」은 주체마다 다르다(태스크 1 리뷰 M1 → 메인 세션 판정, 스펙 3.3 을 좁힘): **바깥 MCP(개인 토큰)는 일반 채널 + 주인의 DM 전부, 채널 안 에이전트(`via: "agent"`)는 일반 채널 + 그 런의 채널이 DM 이면 그 DM 하나**(시킨 사람의 다른 DM 은 NOT_FOUND) — 프롬프트 주입·모델 오판으로 DM 이 채널 답에 옮겨지는 길을 막는다. `list_channels`(행마다 `kind`)·`search_messages`·`read_messages`·`list_conversations`·`get_channel`·`get_run` 이 같은 함수(`auth/channel-access.ts readableChannelSqlFor` — 저장소·검색 함수는 사람 id 또는 이 SQL 을 `ChannelReader` 로 받는다)를 쓴다. REST 검색·읽지 않음은 사람 범위(일반 채널 + 내 DM).
- **PD4 — 팬아웃.** DM 의 `channel.created`·`channel.updated`·`channel.activity`·`approval.requested`·`approval.resolved` 는 workspace 룸이 아니라 주인의 user 룸(`userRoom(dmOwnerId)`)으로만. 채널 룸은 `channel.subscribe` 가 접근 판정을 지나야 들어가므로 그대로. DM 의 `system.notice`(프롬프트 동기화 실패)는 주인 user 룸으로, `#채널이름` 대신 「DM」. 버스 `system.notice` 페이로드에 `userId?` 를 둔다(있으면 그 사람의 user 룸, 없으면 전체). 채널 사실을 workspace 룸으로 내는 이벤트는 `realtime/events.ts channelAudience` 를 거치고, 페이로드에 채널 행이 없으면 채널을 읽어 고른다(없는 채널이면 보내지 않는다)(태스크 2).
- **PD5 — 운영 화면.** `GET /api/v1/ops/runs` 는 DM 런을 채널 이름·주인 없이 「DM」 한 줄로 합친다. `ops/events` 의 key `channel:<id>`(채널 id 만, 내용 없음)는 그대로 둔다. 자동화 대상이 DM 이면 `VALIDATION`(만들기·바꾸기 둘 다). 운영 표의 「DM」 줄은 `OpsRunsRow { id: OPS_DM_ROW_ID, kind: "dm" }` 이고 웹은 링크로 만들지 않는다. 제어 쓰기의 운영 사건 `control_change` 는 DM 이면 `detail.channelId` 를 null 로 싣는다. 자동화 만들기·바꾸기는 남의 DM 404 → 내 DM VALIDATION → 보관 409 순, 게시(지금 실행·웹훅·예약)도 DM 이면 VALIDATION 으로 아무것도 남기지 않는다(태스크 2).
- **PD6 — DM 의 런.** 라우터는 DM 이면 멘션과 상관없이 그 DM 의 에이전트에게 사람의 모든 normal 최상위 메시지를 보낸다(채널 `autoRespond` 행이 이미 그렇게 고른다 — DM 에서는 다른 후보가 없음을 테스트로 고정). DM 에서는 멘션 토큰화·`joinChannelIfAbsent`(보낸 사람 말고)·릴레이가 없다 — 사람 글·에이전트 글 둘 다 `@핸들` 은 평문으로 남는다. `threadRootId` 가 있으면 `VALIDATION`. 채널 `dailyRunLimit` 은 DM 에 걸지 않는다(워크스페이스 상한만). DM 본문은 토큰 꼴(`<@u:…>`)도 `neutralizeMentionTokens` 로 중화하고 `mentions` 는 늘 비운다(`messages/service.ts plainInDm`) — 자동 참여·멘션 푸시·릴레이가 따로 갈래 없이 꺼진다(태스크 3). `dmAccess` 철회·끄기는 새 쓰기를 막고, 철회 전에 줄 선 런도 차례가 오면 보내지 않고 `aborted`(시스템 메시지 없음)로 닫는다(`runs/orchestrator.ts dmClosedTarget`). 이미 어댑터로 간 런은 끝까지 돌고 주인이 그 승인을 결정하며 답은 저장·푸시된다(태스크 3 리뷰 L1 → (b)).
- **PD7 — 승인 결정자.** DM 의 모든 승인(도구 승인·exec 승인·제어 확인 카드)은 DM 주인만 결정한다(역할 무관 — member 주인 포함). 승인 푸시도 주인에게만(지금의 「owner·admin 전원」 갈래를 DM 에서 끈다). 푸시는 트리거 갈래 말고도 발송 직전 거름(`push/service.ts`)이 DM 을 겨눈 알림을 주인 말고 모두 걷는다. 본문의 자리 이름은 「DM」(태스크 2).
- **PD8 — 헤더.** `InboundDeliver` 에 `dm?: { ownerHandle: string }`. 플러그인 헤더와 러너 턴 사실(`buildTurnFacts`)이 `[dodok context]` 줄 바로 다음(세션 줄 앞)에 shared `formatDmLine(ownerHandle)` 을 넣는다. 「이 DM 의 지시」는 채널 프롬프트 자리(`channelPrompt`)로 간다. **플러그인 재설치가 필요하다**(옛 플러그인은 `dm` 을 버리고 받아 DM 줄이 없다). 러너 턴 사실·채널 규칙은 서버(runner-adapter)가 만들므로 `dodok-runner` 는 그대로다. 헤더 참여자는 `buildInboundDeliver` 가 DM 이면 주인 + 그 에이전트로 거른다(멤버 행 불변에 기대지 않는다). DM 이면 릴레이 규칙 줄은 「DM 에는 릴레이가 없습니다 — @핸들은 글로만 남습니다.」, 러너 쪽 자리 이름은 `#dm` 이 아니라 DM(태스크 4).
- **PD9 — DM 지시·관리 경로.** DM 의 `PATCH /api/v1/channels/:id` 는 `prompt` 만 받고 주인만(역할 무관). 그 밖의 채널 관리(이름·주제·멤버 추가·제거·바꾸기·보관·세션 관리자·세션 정책·`dailyRunLimit`·제어 쓰기 도구 전부)는 DM 에 `VALIDATION`. 세션 제목 바꾸기·닫기·다시 열기는 지금 정책 그대로(주인이 만든 사람이다). DM 에 채널 쓰기 제어 도구가 모두 VALIDATION 이라 DM 에서 뜨는 확인 카드는 채널을 받지 않는 도구(`create_channel`·에이전트 도구)뿐이다 — 확인 카드 제목의 「DM」 갈래는 방어선으로만 남는다(태스크 3).
- **PD10 — 읽지 않음.** DM 의 에이전트 normal 메시지는 모두 「나를 멘션한 글」로 센다(사이드바 DM 줄의 배지). 일반 채널 규칙은 그대로. 실시간도 같은 규칙이다 — `channel.activity` 는 DM 에이전트의 보통 메시지면 `mentionedUserIds` 를 `[dmOwnerId]` 로 싣는다(`realtime/events.ts`). 그래서 웹은 DM 을 따로 가르지 않고 지금 배지 규칙으로 센다(태스크 3 수정).
- **PD11 — DM 푸시.** DM 의 에이전트 normal 최상위 메시지(정본)와 `run_error` 는 주인에게 푸시(누가·어디만, 본문 없음). tag `dm:<conversationId>`. 그 세션을 보고 있으면 거름(지금 규칙). payload `kind` 는 `"mention"`(새 값 없음), 제목 `@<핸들><이/가> 답했습니다`, 본문 「DM」. run_error 의 「누가」는 DM 에이전트(태스크 3).
- **PD12 — 날짜 묶음은 브라우저 시간대**(스펙 8장 빌더 몫). 오늘·어제·이번 주(오늘 포함 7일)·이전, `lastMessageAt`(없으면 `createdAt`) 기준.
- **PD13 — `dmAccess` 는 제어 도구로 바꾸지 않는다.** `update_agent` 스키마에 넣지 않는다(로드맵 결정 — 채널 안 에이전트가 확인 카드 하나로 DM 범위를 넓히지 못하게). REST `PATCH /api/v1/agents/:id { dmAccess }` 만(admin 이상).

## Review Focus

1. **admin 이 남의 DM 에 역할 정책이 있는 쓰기를 보냄(`PATCH /channels/:id`·`PATCH /conversations/:id`·`approval.resolve`·멤버 추가)** — 403 이 아니라 404. → 태스크 1(매트릭스 `DM_CASES` 가 접근 판정이 먼저인지 본다).
2. **검색 결과가 남의 DM 에 수백 개 걸림** — 페이지·cursor·`total` 이 남의 DM 을 센 흔적 없이 맞다(SQL 단계 거름). → 태스크 1.
3. **DM 주인이 admin → member 로 강등되고 그 에이전트는 `dmAccess: admins`** — DM 은 그대로 읽히고(사라지지 않는다), 쓰기는 409 `DM_READ_ONLY` `dm_not_allowed`, admin 으로 되돌리면 이어 쓴다. → 태스크 3.
4. **두 탭 — 한 탭에서 admin 이 에이전트를 보관하는 사이 주인이 DM 에 보내는 중** — 보내기는 409 `DM_READ_ONLY`, 웹 항목은 「다시 보내기」 없이 사유로 남고 작성기 자리가 사유 줄로 바뀐다(`agents.changed` → DM 목록 다시 받기). → 태스크 3(서버)·태스크 5(웹).
5. **에이전트가 DM 답에 `@mia` 를 씀** — 평문으로 남고 mia 는 채널 멤버가 되지 않으며 멘션 푸시·읽지 않음 배지를 받지 않는다. → 태스크 3.

각 줄의 테스트는 해당 태스크의 단계에 들어 있다.
