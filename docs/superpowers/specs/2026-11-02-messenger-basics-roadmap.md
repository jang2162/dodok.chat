# 기본 메신저 기능 — 로드맵

**상태**: 순서 확정(2026-11-02, 사용자 승인). 하위 스펙은 B(프로필)부터 하나씩 쓴다 — 지금 있는 것은 B 하나다.
**범위**: 사용자 요청(2026-11-02) 「아직 기본적인 메신저 기능들이 부족해. 다른 메신저에서 가져올만한 기능들 참고해서 가져와줘. 프로필설정, 사용자간 DM, 파일관리 등」. 후보 A~K 가운데 사용자가 고른 1차 묶음 A·B·C·D.

**앞선 근거**:
- 지난 로드맵의 후보 표 `docs/superpowers/specs/2026-10-25-sessions-dm-runner-roadmap.md` 「Slack 류 앱에서 가져올 만한 기능」 — 이 묶음의 A·C·「사람 상태」가 거기서 왔다.
- 접근 판정 `apps/server/src/auth/channel-access.ts`(에이전트 DM 스펙 `docs/superpowers/specs/2026-10-25-agent-dm-design.md` 결정 2).
- 팀 스펙 `docs/superpowers/specs/2026-09-26-team-members-design.md` 「열린 문제」 — 멤버 아바타 올리기·접속 상태, 비공개 채널, 채널 참여·나가기.

## 1차 묶음과 순서

각자 「스펙 → 계획 → 구현」을 따로 밟는다.

| 순서 | 하위 프로젝트 | 무엇 | 스펙 | 의존 |
| --- | --- | --- | --- | --- |
| 1 | **B 프로필** | 사람·에이전트 프로필 패널, 아바타 올리기, 상태(자동 접속·수동 상태·상태 메시지·방해 금지), 에이전트 소유자 | `docs/superpowers/specs/2026-11-02-profiles-presence-design.md` | 없음 |
| 2 | **C 사람 간 DM** | 사람끼리 1:1·그룹 DM | `docs/superpowers/specs/2026-11-03-human-dm-design.md` | B(DM 목록의 아바타·접속 점) |
| 3 | **A 메시지 수정·삭제** | 내가 쓴 글 고치기·지우기, 에이전트가 이미 읽은 글의 처리 | (아직 없음) | C(누가 고치고 지우나가 C 의 접근 규칙 위에 선다) |
| 4 | **D 파일함** | 채널·DM 마다 사진·파일 모아 보기·검색·필터 | (아직 없음) | C(누가 어떤 파일을 보나가 C 의 접근 규칙 위에 선다) |

**순서의 까닭(사용자 기준 「개발하기 편한 순서」)**: C 는 「DM = 주인 사람 하나 + 에이전트 하나」라는 전제(접근 판정 `canReadChannel`·`channels_dm_pair` 유일 인덱스·DM 라우터의 자동 응답·푸시 거르기 `reachable`)를 다시 세운다. A·D 는 그 판정 위에서 「누가 고치나」·「누가 보나」를 정하므로 C 뒤에 두면 한 번에 맞게 만든다. B 는 다른 셋과 얽히지 않고, C 의 DM 목록이 B 의 아바타·접속 점을 쓴다.

## 1차에서 뺀 후보

E 고정 메시지 · F 채널별 알림 끄기 · G 인용 답장 · H 사람 입력 중 표시 · I 저장한 메시지 · J 링크 미리보기(서버가 남의 URL 을 가져온다 — SSRF 방어) · K 비공개 채널·참여·나가기(`docs/guides/plan.md` 8장 「이월」 「팀」 묶음의 「스펙 「열린 문제」」 줄). 다음 묶음에서 다시 고른다.

- F 는 B 의 「방해 금지」(사람 단위로 알림을 멈춘다)와 다르다 — F 는 채널·DM 단위다.
- H 는 wire `typing` 이 이미 양방향에 있다(`packages/shared/src/wire/index.ts`). 고를 때 지금 웹이 사람의 입력 중을 그리는지부터 본다.
- K 는 `channels.visibility`(`public`·`private`) 열이 있으나 아무 데서도 막지 않는다. C 가 접근 판정을 넓힐 때 K 가 같은 함수에 규칙을 더하는 자리를 남긴다.
