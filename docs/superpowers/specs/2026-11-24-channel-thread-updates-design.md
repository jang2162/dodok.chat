# 채널 세션에 스레드 소식 — 설계

상태: 승인 대기(2026-11-24) · 결정: 사용자와의 대화(2026-11-24), 빌더 확인 1회

## 1. 왜

같은 세션에서 스레드로 바로잡은 사실을 채널 세션의 에이전트가 모른 채 옛 정보로 답했다(사용자, 2026-11-24). guideline 에이전트가 스레드에서 「erdd 의 pick 폼은 이미 제출됐다」를 확인하고 사과까지 했는데, 뒤이어 채널에서 「각 작업 현황」을 묻자 erdd 를 「pick 폼 대기」로 답했다.

원인은 설계다. 채널 런의 문맥(`apps/server/src/modules/runs/context.ts` `buildInboundDeliver`)은 그 대화의 최상위 글 최근 20개만 싣고 스레드 답글을 뺀다(`docs/guides/agent-guide.md` 「채널 세션은 스레드에서 오간 말을 모른다」, `docs/guides/plan.md` 8장 스레드 항목 「채널 런의 문맥에서도 스레드 답글을 뺀다」). 스레드 세션(`…:thread:<rootId>`)과 채널 세션은 기억을 나누지 않으므로, 스레드에서 오간 말은 채널 세션에 들어갈 길이 없다.

## 2. 목표 · 하지 않을 것

**목표**
- 채널(대화) 세션의 런이, 그 세션이 지난번에 받은 뒤 그 대화의 스레드들에 새로 달린 답글을 헤더에서 본다.
- 같은 소식은 한 번만 간다(반응과 같은 커서 방식).
- OpenClaw 플러그인과 러너가 같은 문구를 받는다.

**하지 않을 것**
- 스레드 세션이 채널이나 다른 스레드의 소식을 받는 것 — 스레드 세션은 지금처럼 루트와 그 스레드 답글만 본다.
- 스레드 내용을 모델로 요약하는 것 — 원문을 잘라 싣는다.
- 세션 분리(세션 키·하위 세션 규칙) 자체를 바꾸는 것.
- 웹 화면 변경.
- 커서 뒤에 **수정**된 답글을 다시 알리는 것 — 새로 단 답글(`created_at`)만 본다. 수정으로 바로잡은 것은 이번 범위 밖(사용자 결정).

**실패로 볼 것(돌아가도)**
- 다른 대화(같은 채널의 다른 세션)의 스레드 답글이 실리는 것.
- 같은 답글이 턴마다 되풀이되는 것.
- 스레드가 많은 대화에서 헤더가 상한 없이 커지는 것.
- 옛 플러그인·옛 러너가 그 칸을 버렸는데 커서만 올라 소식이 사라지는 것.

## 4. 무엇이 실리는가

**범위** — 이 런이 대화 세션 런(`run.threadRootId` 없음)일 때만. 그 대화(`conversationId`)의 `kind = 'normal'` 스레드 답글(`thread_root_id` 가 있음) 가운데 `created_at > thread_replies_seen_at` 인 것. 일반 채널·그룹 DM 모두(스레드가 있는 곳). 1:1 에이전트 DM 은 스레드가 없어 실릴 것이 없다.

**상한**(조율자 값 — 빌더가 시험으로 조정해도 되지만 상한 자체는 둔다)
- 스레드 최대 5개 — 새 답글이 가장 최근에 달린 스레드부터. 밖으로 밀린 스레드 수는 `omitted` 로.
- 스레드마다 최근 답글 최대 3개, 그 스레드의 새 답글 총수는 함께 싣는다.
- 답글 본문은 300자에서 자른다(`clip` 과 같은 서러게이트 처리). 첨부는 `attachmentPlaceholder` 자리표시.
- 루트는 발췌로만 — 반응의 `excerptOf` 와 같은 변환, 60자(`REACTION_EXCERPT_MAX`). 루트 메시지 id 도 싣는다(에이전트가 제어 도구로 그 스레드를 읽을 수 있게).

**문구**(예 — 정확한 낱말은 빌더 몫, 머리줄의 「지난 턴 뒤」 뜻은 지킨다)

```
스레드 소식(지난 턴 뒤 이 세션의 스레드에 새로 달린 답글):
- 「제출하면 erdd 가 orca.yaml 의 옛 경로를…」 새 답글 4(최근 3):
  [17:28] @owner: 제출 된 폼인데?
  [17:29] @guideline: 제가 잘못 말했습니다. 폼은 이미 제출됐는데…
  [17:29] @guideline: @erdd 폼은 이미 제출됐습니다. 이어서 진행해 주세요.
(외 스레드 2개)
```

자리는 플러그인 헤더(`packages/openclaw-plugin/src/context.ts` `formatInboundContext`)에서 「최근 대화」 다음·반응 앞, 러너는 반응 사실과 같은 `buildTurnFacts`(`packages/shared/src/runner/prompt.ts`, 서버의 러너 어댑터가 부른다) 안의 반응 앞. 러너 머신에서 도는 `renderRunnerPrompt` 는 고치지 않는다 — 러너 판을 올리지 않아도 된다. 시각은 「최근 대화」에 쓰는 `hhmm` 그대로.

## 5. 계약·저장

- `packages/shared/src/bridge/index.ts` — `InboundThreadUpdate`(루트 id·루트 발췌·새 답글 수·최근 답글 배열 ≤3, 답글은 `InboundContextMessage` 꼴 + 본문 상한)와 `InboundContext.threadUpdates`(배열 ≤5, 선택)·`threadUpdatesOmitted`(정수 ≥1, 선택). 상한 상수는 반응처럼 shared 에서 내보내 서버가 그 값으로 자른다.
- `BridgeCapability` 에 `threadUpdates`. 어댑터의 `supports(…, capability)` 유니온(shared `AgentAdapter`, OpenClaw `gateway-connection.ts` 의 좁힌 유니온)에 더한다. 러너 어댑터의 `supports` 는 이 능력에 늘 true.
- 공용 문구 함수(가칭 `formatThreadUpdates`) — shared, 반응 함수 옆. 비면 "".
- 마이그레이션 0043 — `agent_sessions.thread_replies_seen_at`(nullable 시각). 기존 행은 마이그레이션 시각으로 채운다(옛 답글을 한꺼번에 싣지 않게). 새 행은 `ensureSession` 이 만든 시각으로(새 세션은 그 전 답글을 받지 않는다). 스레드 세션 행에도 열은 생기지만 쓰지 않는다.

## 6. 서버 흐름

오케스트레이터 디스패치(`apps/server/src/modules/runs/orchestrator.ts`, 반응을 고르는 자리 바로 옆)에서 반응과 같은 순서를 따른다.

1. 대화 세션 런이고 그 연결이 `threadUpdates` 를 지원할 때만 고른다. 세션 행은 갱신 판정(`renewSessionOnPromptChange`) 뒤에 다시 읽는다 — 새 세션으로 열었으면 커서도 지금으로 올라야 한다(반응과 같은 까닭). 지금 `renewSessionOnPromptChange`(`apps/server/src/modules/sessions/service.ts`)는 `reactionsSeenAt` 만 올리므로 같은 자리에서 `threadRepliesSeenAt` 도 올린다(빌더 확인).
2. 고른 결과에서 `latestAt` = 고려한 새 답글 전체(보여 준 것과 `omitted` 로 센 것 모두) 가운데 가장 늦은 시각. 보이지 않은 스레드도 「외 N개」로 알렸으므로 다음 턴에 다시 싣지 않는다.
3. send 가 받아들여진 경로에서만 커서를 `latestAt` 으로 올린다(뒤로 가지 않음). send 실패·drop·ack 전 중지면 그대로 — 다음 런에 다시 실린다. ack 를 기다리는 사이 달린 답글은 `latestAt` 보다 늦어 다음 런에 남는다. 커서가 null 인 행은 싣지 않고 지금으로 채운다.
4. 지원하지 않는 OpenClaw 연결이면 싣지도, 커서를 건드리지도 않는다 — 플러그인을 올린 뒤 첫 턴에 그동안 쌓인 것이 상한 안에서 실린다.

명령 런·이어가기·상호작용 런은 반응이 실리는 런과 같은 규칙을 따른다(반응을 싣는 런이면 이것도 싣는다).

## 7. 문서

- `docs/guides/agent-guide.md` — 「채널의 최근 대화에는 스레드 답글이 들어가지 않는다 — 채널 세션은 스레드에서 오간 말을 모른다」 줄과 「스레드의 에이전트가 채널에서 한 말을 모른다」 문제 줄 근처: 최근 대화는 그대로 최상위만, 대신 「스레드 소식」 줄로 지난 턴 뒤 새 답글이 온다(상한·자르기 포함). 스레드 세션 쪽은 그대로임을 함께.
- `docs/guides/plan.md` — 8장 스레드 항목의 「채널 런의 문맥에서도 스레드 답글을 뺀다」 뒤에 이 변경을 잇고, 10장 결정에 T1·T2 를 한 줄로.
- 플러그인 판이 올라가므로 `docs/guides/live-smoke.md`·원격 업데이트 안내에 새 능력이 필요한 것이 있으면 따라 고친다(빌더 판단).

## 8. 접근 (고른 것과 버린 것)

1. **선택 필드 + 공용 문구 + 새 커서(고름)** — 반응이 이미 걸은 길이라 계약·커서·문구 함수의 꼴이 정해져 있다. 대가는 플러그인 재설치(원격 업데이트로 된다)와 능력 플래그 하나.
2. **「최근 대화」 줄에 끼워 넣기(버림)** — 플러그인을 안 고쳐도 되지만 20개 상한을 스레드 줄이 먹고, 스레드 답글인지가 글자 관례에만 있고, 루트가 20개 밖인 스레드는 놓을 자리가 없다.
3. **매 턴 스냅샷(버림)** — 상태가 없어 단순하지만 같은 꼬리가 턴마다 되풀이되고 루트가 20개 밖인 스레드를 놓친다.
4. **커서 열 없이 직전 채널 런 시각으로 계산(버림)** — 실패·중지 런을 어떻게 셀지 애매하고 반응 커서와 규칙이 갈린다.
