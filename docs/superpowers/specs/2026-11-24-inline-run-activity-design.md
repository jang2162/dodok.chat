# 응답 안의 활동(추론·도구) — 설계

날짜: 2026-11-24 · 상태: 승인(2026-11-24)

## 왜

사용자 요청: Orca 채팅 UI 처럼, 에이전트가 답하기 전까지 부른 도구와 추론을 보다가 답이 나오게 하고, 응답마다 진행한 활동을 확인할 수 있게 한다. 지금은 도구 기록이 오른쪽 「활동」 탭에서 런을 골라야만 보이고, 채팅에는 답 글만 나온다. 추론은 아무 데도 남지 않는다.

## 목표

- 런이 도는 동안 스트리밍 버블 안에 추론·도구 줄이 실시간으로 쌓인다.
- 답 글(첫 텍스트 델타)이 오면 그 묶음은 한 줄 요약으로 접힌다. 누르면 펼친다.
- 확정된 에이전트 메시지(`runId` 가 있는 것)에도 같은 요약 줄이 남고, 펼치면 저장된 런 이벤트로 다시 그린다.
- 펼친 줄의 도구는 활동 탭과 같이 「인자 보기」·「결과 보기」, 승인 표시.

## 비목표

- 활동 탭 제거·변경(그대로 둔다).
- 추론을 누구에게만 보이는 권한 구분 — 런 이벤트는 지금도 그 대화를 볼 수 있는 사람 모두가 본다. 추론도 같은 규칙.
- 추론을 에이전트에게 다시 먹이기(헤더·기억) — 화면 표시만.

## 모양

```
@dev  ▾ 활동 · 추론 · 도구 4 · 12초        ← 접힌 요약(누르면 펼침)
      ┊ 💭 테스트 실패 원인부터 보자…
      ┊ ✓ Read  src/app.ts            0.2초
      ┊ ⟳ Bash  pnpm test             ← 진행 중이면 맨 아래 줄이 살아 움직임
      답 본문…
```

- 진행 중이고 답 글이 아직 없으면 펼친 채, 답 글이 시작되면 접힌다(사람이 손으로 펼쳤으면 그대로 둔다).
- 추론 줄은 접힌 상태에서 첫 줄만, 펼치면 전체(마크다운 없이 흐린 글).
- 도구·추론이 하나도 없는 런(바로 답한 런)은 요약 줄을 그리지 않는다.
- 확정 메시지는 처음에 요약 줄만 그리고, 이벤트는 펼칠 때 `GET /api/v1/runs/:id/events` 로 받는다(화면의 모든 메시지마다 미리 받지 않는다). 그 탭에서 막 끝난 런은 런 스토어에 이미 있는 이벤트를 쓴다. 미리 받지 않은 메시지의 요약 줄은 「활동」만 적고, 받은 뒤에 수를 붙인다.
- 스레드 패널·DM 에서도 같다.

## 데이터

- 새 런 이벤트 `REASONING_MESSAGE_CONTENT { messageId, delta }`(+ `REASONING_MESSAGE_START`·`REASONING_MESSAGE_END`) — AG-UI 이름을 따른다. shared `events` 에 더한다.
- **Claude 러너:** SDK `stream_event` 의 `content_block_start`(type `thinking`)·`content_block_delta`(`thinking_delta`)를 러너 → 서버 계약의 새 항목으로 싣는다. 지금은 `stream-map.ts` 가 버린다. 모델·설정에 따라 thinking 이 요약이거나 비어 있을 수 있다 — 그때는 START/END 만 와서 「생각 중…」만 보인다. 옛 러너는 보내지 않을 뿐 깨지지 않는다(서버는 새 항목을 모르는 러너에게 아무것도 요구하지 않는다).
- **OpenClaw:** Gateway agent 프레임의 `stream: "thinking"` 을 같은 이벤트로 매핑한다(지금은 `events.ts` 가 무시). 프레임 모양은 빌더가 실물·기존 스파이크 문서로 확인한다.
- **저장:** 오케스트레이터가 텍스트 델타처럼 추론 델타도 코얼레싱해 `run_events` 에 남긴다. 런 하나의 추론 글은 **20,000자까지** 저장하고 넘치면 자른 표시를 남긴다(내 판단 — 긴 추론이 DB 를 키우지 않게).
- 메시지 ↔ 런은 기존 `Message.runId` 로 잇는다.

## 접근

하나뿐이다. 활동 탭을 키우는 것은 「채팅 안에서 보다가 답이 나온다」를 풀지 못하고, 메시지에 활동 요약을 서버가 미리 붙이는 것은 펼칠 때 받는 것보다 저장·계약이 늘어난다.

## 빌더에게 남긴 것

- OpenClaw thinking 프레임의 실제 모양과 델타/스냅숏 여부.
- 요약 줄의 정확한 글(「추론」 표시 여부, 걸린 시간 계산 — 첫 이벤트~첫 텍스트 델타).
- 런 이벤트 보존 기간이 이미 있는지 — 있으면 지난 메시지의 펼침이 「기록이 없습니다」로 끝나는 꼴.
- 추론 저장 상한 20,000자가 실제 런에서 충분한지(런 0회 하네스로는 모른다 — 보고에 적는다).
- 문서: `docs/manual/user-guide.md`(활동 탭 절 옆에 「응답 안의 활동」), `docs/guides/agent-guide.md` 는 바뀌지 않는다(에이전트가 받는 것은 그대로).
